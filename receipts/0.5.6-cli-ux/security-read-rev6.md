# Security read, mash 0.5.6 cli-ux revision 6 (draft)

Reviewer attestation: this security runs on model gpt-6-sol, Daybreak ON (codex -c daybreak=true), codex-cli 0.170.0, read-only sandbox.

I read the supplied workspace text and ran nothing. The DRAFT5 helper and skill were not supplied, so this is a review of the contract (contract-0.5.6-cli-ux-rev6-draft.md), not their implementation. This draft has no literal §5 credential table or `NFR-002`/`NFR-003`; the relevant text is `REQ-002`, `REQ-003`, `REQ-010`, `REQ-011`, `REQ-013`, and §5’s invariants and custody statement.

## Threat model

The assets are signing seeds, endpoint credentials, TLS keys, stored mail, and the server identity a client accepts. An installing agent may have a shell and terminal while acting on a brief request. Other processes under its OS account can read or change that account’s files; other host users can reach a loopback TCP listener. The boundaries that matter are person to agent, local file ownership to same-user control, downloaded artifact to executed code, and a token’s claims to independently established server trust.

## Rev 5 findings: disposition

“Closed” below means rev 6 supplies a requirement and a reviewer-checkable acceptance condition. It does not mean code has passed.

## Credential and trust inventory

| Material | Where it lives and who can read it | Agent authority; argv, log, and receipt exposure |
|---|---|---|
| CA key; server TLS key | Initially in the helper’s 0700 directory (`REQ-002`, §3). §5 says the CA key can move offline. The contract does not identify the server key’s final path or reader. Same-user and privileged processes can read owner-accessible copies. | An agent can run the helper. `INV-001` and `INV-003`, §5 forbid private-key values in output, argv, logs, JSON, and receipts; `AT-007` scans those channels. Paths and file modes after server startup need evidence. |
| Operator and account signing seeds | `mashctl` retains them in its 0700 config directory as 0600 files (§5 “Custody of setup secrets”). Same-user processes and backups can obtain them. | A holder can mint identities and read every agent’s mail. An agent running adoption gains access under that OS account. Seed **values** are barred from argv, logs, and receipts; the contract allows paths in status detail. |
| System and admin credentials | Export directory, then `mashctl`’s config after `adopt --from` (`REQ-002`, `REQ-011(ii)`, §3). Same-user processes can read copies. | The agent can invoke adoption and use signing authority. `INV-003`, §5 bars credential values from argv and output; `AT-007` scans receipts. Source-directory authenticity is a custody assumption, not independently proven. |
| Endpoint key, token, installed credentials | Input files or stdin; installed 0600 files in the current user’s mash config (`REQ-003`, `INV-003`, §3 and §5). Same-user processes can read them. | An agent may pass **paths** to `credential install`, never values in argv. Existing different secrets must be refused. `AT-007` checks value leaks, but not sensitive information disclosed by printed read paths. |
| Account public key, CA certificate, fingerprint, address, `trust.json` | `REQ-013`, §3 puts the binding in a 0600 file in mash config; config and CA are separate files. The same OS user can replace owner-writable trust state. | First install and `mash trust replace` can establish or change trust after typed confirmation. Values are public, but substitution is security-critical. A 0600 mode and an exclusive create do not make this record tamper-resistant against the agent’s own OS account. |
| Server log, archives, receipts | `AT-007`, §6 requires a 0600 server log and retention described by the guide. Archives intentionally contain secrets; receipts must not contain secret values. | The helper can create archives and remove keys (`REQ-002`, §3). `AT-007` requires canary scans, but archive destination/readers and receipt disclosure through paths need explicit checks. |

## Findings

**F6-1 — CARRIED `R5-4`; blocking; high certainty. `REQ-013`, §3; `REQ-003`, §3; `AT-007`, §6.** On first use, an attacker supplies a token signed by the account key it names and directs an agent to an attacker-controlled server and CA. “Signature is verified” does not say what independent key or authority validates the issuer; verifying against the token’s own claimed issuer would prove only self-consistency. The first server address is said to be supplied separately, but `REQ-003` explicitly requires typing the *fingerprint*, while `INV-004` ambiguously says to type the address or fingerprint back. **Smallest change:** define JWT signature and issuer verification against an independently obtained account key or state explicitly that first-use account identity is accepted only through the separately confirmed operator channel. Require the person to confirm both the intended address and CA fingerprint from that channel before first write. Make `AT-007` reject a self-signed attacker token, attacker address under an otherwise valid CA, and a token whose issuer differs from the independently established account key.

**F6-2 — CARRIED `R5-4`; blocking; high certainty. `REQ-013`, §3; `REQ-003`, §3; §7 “Residual risks for Randy’s written acceptance.”** After a sound first install, an agent or process under the same OS account replaces `trust.json` and matching config files with attacker-chosen values. Exclusive creation and mode 0600 stop some other users and accidental overwrite; they do not stop the owner replacing a pathname. A later install could then validate against attacker-controlled state. “An altered config” is named in `REQ-013`’s acceptance list, but no independently protected reference is specified for detecting a coordinated replacement. **Smallest change:** state the precise limit: trust files protect against other OS users and accidental changes, while same-user processes can replace them. Require every use to reject disagreement among `trust.json`, config, and CA, and test a coordinated same-user replacement. If the design keeps this boundary, obtain **mash-specific written acceptance** of the remaining same-user substitution risk.

**F6-3 — CARRIED `R5-9`; blocking; high certainty. `REQ-003`, §3; `REQ-013`, §3; `AT-007`, §6.** `--replace` prepares `config.json`, `ca.pem`, and `trust.json`, then says they are “renamed into place as one step.” Ordinary renames of three names are separate operations. A crash between them can leave a new CA with an old address or account pin. Moving an old credentials file aside before replacement creates another interruption point; “old state working” is not guaranteed. The contract simultaneously says install cannot change the trust record and calls `--replace` an install trust change. **Smallest change:** make `mash trust replace` the only trust mutation path, define a single commit point such as an atomic pointer to a complete new versioned directory, and specify the credentials-file precondition and recovery command. Test interruption before and after each write and commit, compare all old bytes after refusal, and verify a later command selects one complete generation. Define account-key rotation through that same confirmed command, including refusal and recovery when the old key or server is unavailable.

**F6-4 — CARRIED `R5-5`; blocking; high certainty. `REQ-011(ii)`, §3; `REQ-002`, §3.** A same-user agent prepares an internally consistent source directory and asks `mashctl adopt --from` to copy it. Ownership and mode checks pass. A CA certificate and NATS account credentials can each validate individually without proving that this CA authenticates the intended account or server; the phrase “belong together cryptographically” supplies no protocol or artifact that binds them. File-replacement detection also lacks a stated held-handle or verified-byte rule. **Smallest change:** enumerate each check: credential signature against the account key, any operator-to-account signing chain, server certificate and hostname against the source CA, and an independently supplied intended address or an explicit statement that local source custody is the sole origin of that address. Bind adoption to bytes read through held directory handles and compare the copied bytes. Test a fully consistent attacker-prepared directory as an accepted **custody residual**, plus mixed files and a swap that must refuse. A person must accept the same-user prepared-source risk for mash if retained.

**F6-5 — CARRIED `R5-6`; blocking; medium certainty. `REQ-011(i)`, §3; `REQ-002`, §3; §8 “Release mechanics.”** An attacker able to alter the page an agent reads can present a malicious script and matching digest in what the agent treats as a “reviewed README.” Alternatively, a verified downloaded binary can be replaced before the installer copies it. The contract names the release workflow and tag but does not state how the agent obtains an immutable, independently reviewed digest or binds the final installed bytes to those verified. **Smallest change:** pin the reviewed README to a recorded commit or immutable release artifact and name the expected attestation repository, workflow, tag, and subject for script and binaries. Install from a private file descriptor or rehash the exact destination bytes before reporting success. Add script substitution, README-digest substitution, binary substitution, and verification-to-install swap tests, with no executable installed after failed verification.

**F6-6 — CARRIED `R5-7`; blocking; medium certainty. `REQ-011(iii)`, §3; `REQ-002`, §3; `AT-007`, §6.** `mash plugin install` may extract an embedded plugin, then run a Claude Code command that resolves the marketplace name and fetches a different plugin. The binary’s verification would not verify what Claude Code installs. The contract promises “no network fetch” but specifies only that the exact Claude Code command is shown, with no offline acceptance test or destination inspection. **Smallest change:** require that command to install only the extracted, verified local bytes, pin its digest to the binary, refuse if the requested scope or destination differs from the invoking user’s configuration, and test with network unavailable and a substituted marketplace entry. Record the installed bytes and actual destination in `AT-007`. Any later widening of plugin permissions or installation scope must be handed to the person under `INV-004`, §5.

**F6-7 — CARRIED `R5-1` and `R5-2`; blocking pending written acceptance; high certainty. `INV-004`, §5; `REQ-002`, §3; §7 “Residual risks for Randy’s written acceptance.”** An agent with terminal control can type the confirmation itself; a same-user process can swap a checked helper path before the subsequent write, archive, or removal. Rev 6 now describes both attacks, but `INV-004` still claims an agent driving a shell “cannot supply” the answer, and `AT-007` does not exercise all three path operations. **Smallest change:** remove that claim, test a correct answer via agent-driven PTY, and require swapped-path tests at creation, archive, and removal that inspect the unintended destination. Present `S1` and `S2` as separate concrete outcomes for **Randy’s written acceptance for mash**. Randy’s earlier homerange acceptance establishes precedent, not acceptance of this contract.

**F6-8 — CARRIED `R5-3`; blocking pending written acceptance; high certainty. `REQ-010`, §3; §7 `S4`; `AT-007`, §6.** A parent starts the installing agent with `MASH_INSECURE_PLAINTEXT=1`. A later connection can send the authentication exchange and mail over an unencrypted local connection without a fresh user choice; warnings do not stop that sequence. `S4` now says this plainly. **Smallest change:** either require a fresh destination-specific choice before connection and test that no sensitive network bytes leave first, or retain the behavior and obtain **separate written acceptance** for mash. A plaintext loopback connection exposes traffic to the server and to processes able to observe or interpose on that local connection; the contract must not imply that binding `127.0.0.1` limits access to the installing user.

**F6-9 — NEW; nonblocking; high certainty. `REQ-002`, §3; `AT-007`, §6.** The helper may print paths and create a server log, while the acceptance test only says that the log is 0600 and kept no longer than “the guide says.” No retention period is in this contract, and `AT-007` does not require checking the exact commands and receipts for sensitive *path* disclosure. An agent could leave a long-lived log or publish an owner-revealing source path while passing value-canary scans. **Smallest change:** state the maximum log lifetime and who deletes it; require `AT-007` to inspect log mode and retention plus the exact guide command, diagnostics, and receipt forms for read-path disclosure.

## Other gaps and acceptance boundary

`REQ-002`, §3 specifies default loopback binding but has no `NFR-003` or equivalent inventory of which NATS endpoints are reachable by **every local user**, what authentication each requires, and what remains observable under `REQ-010`. The default protects against remote network access, not local-user connection attempts. Add a test from a second OS user against each listening port, including the plaintext override.

`INV-004`, §5 governs trust, exposure, and destruction, but `REQ-011`, §3 gives an agent a broad setup path under a sparse request. The contract should say which steps the agent may execute after “set this up” and which require a person to choose the source release, local source directory, server address, plugin scope, or changed permissions. Its own terminal cannot prove that choice. This is the missing authority rule corresponding to the requested `NFR-002`.

The §7 bundle is not one uniform risk. `S1` is agent impersonation of a confirmation; `S2` is a pathname race in the helper; custody is direct same-user access to signing authority and mail. They may be presented together, but each needs its own consequence and **explicit mash acceptance**. `S4` is correctly separate. The contract’s `REQ-013` trust-file tampering and `REQ-011(ii)` agent-prepared adoption source should also appear in that acceptance text if the design retains them.

## Summary

I find **8 blocking and 1 nonblocking findings**. Revision 6 closes `R5-8` in the contract and materially improves the other items, but first-use identity, trust-state integrity, atomic replacement, adoption binding, and artifact-to-install verification still need sharper requirements and tests. `F6-2`, `F6-4`’s same-user source risk, `F6-7`, and `F6-8` need a person’s written acceptance if left unfixed; the other blocking findings need contract changes or equally specific acceptance under `contract@0.3.4`. In my view this draft is **not ready for ratification**. I verified text only and ran no helper, installer, binary, plugin, or acceptance test.
