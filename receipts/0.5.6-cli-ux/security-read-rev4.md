Reviewer attestation: this security runs on model gpt-6-sol, Daybreak ON (codex -c daybreak=true), codex-cli 0.170.0, read-only sandbox.

This contract has no section 5 credential table, `NFR-002`, or `NFR-003`. The corresponding boundaries here are chiefly `REQ-002`, `REQ-003`, `REQ-010`, `INV-003`, and `INV-004`.

## Threat model

The assets are signing and TLS keys, NATS credentials, stored mail, and the server identity a client accepts. An installing agent can run commands for a person who may have authorized only “set it up”; another process under that user can also alter files between checks. Other host users can reach a loopback TCP listener, though the intended NATS configuration requires TLS and credentials for account access. The trust boundaries are the person’s decisions, downloaded code, private setup and mash configuration directories, the separately delivered CA fingerprint, and the choice to send credentials and mail over plaintext.

## Credential and trust inventory

| Material | Where it lives; who can read it | Agent action and exposure boundary |
|---|---|---|
| CA private key and server private key | `ca.key` and `server.key` start under the helper’s 0700 directory; the owner and their processes can read them. The server needs `server.key`. After retirement, `ca.key` is in a 0600 archive pending the person’s off-machine move. | An agent may run setup. `INV-003`, §5 bars values in argv, output, logs and receipts. The helper passes file paths to OpenSSL, but a same-user process can read files while they exist. |
| Operator and account signing seeds | `nsc/`, `export/*.nk`, then copies under the owner’s mashctl configuration; the owner and their processes can read each copy. | The agent may create and adopt using **paths**. The helper’s retirement removes its `nsc/` and `export/` copies only after making an archive; mashctl’s needed copies remain. No seed value should appear in argv, diagnostics or receipts under `INV-003`. |
| System and admin `.creds` | Initially `export/*.creds`; `REQ-002`, §3 requires 0600 copies in mashctl’s config. Their holder can exercise the associated NATS authority; the skill says the admin credential can read every agent’s mail. | Adopt receives paths in argv. The guide test’s copy behavior depends on its patch, so actual 0.5.6 custody is unverified. |
| Endpoint private keys and `.creds` | Current user’s selected mash configuration; owner and processes running as that user can read them. | `REQ-003` lets the agent create or install them. `INV-003` bars values from argv, errors, JSON, logs and receipts and requires exclusive, atomic writes. No supplied test runs the proposed credential-install interruption or leak checks. |
| Hand-off token | File or stdin under `INV-003`; the recipient and their processes can read it. | An agent may pass its **path**, never its contents in argv. The token cannot authenticate its own CA: `REQ-003`, §3 requires a fingerprint given separately by the operator. |
| CA certificate, fingerprint, server URL | Public trust inputs in the hand-off and installed user config. | On first install, `REQ-003`, §3 requires the person to type the separately supplied fingerprint, and §5 requires the live server certificate to match that CA and hostname before any write. | Logs, temporary files, archives and receipts | Private command temp file, persistent `server.log`, 0600 backup or retirement archive, terminal output and acceptance records. | `INV-003` prohibits secret contents in outputs and receipts. `REQ-002`, §3 correctly warns that **every local user can reach** the default `127.0.0.1` listener. They can reach the TLS/NATS handshake and any pre-authentication behavior; credentials are meant to prevent account access. `REQ-010`, §3 addresses a separate choice: with its plaintext override, credentials and mail cross that connection unencrypted. Loopback does not make such traffic exclusive to the installing user.

## Findings

**S1 — CARRIED F1; blocking; high certainty. `INV-004`, §5; `AT-007`, §6; helper 377–401 (helper/nats-local-setup.sh:377), 1082–1090 (helper/nats-local-setup.sh:1082); skill 448–455 (helper/2026-11-19-nats-local-skill-DRAFT4.md:448).** An agent starts a PTY, reads the printed address or fingerprint, and sends those same bytes. The helper accepts; its test demonstrates that sequence. The §5 claim that the prompt “stops an agent acting without” a person is therefore too broad. The residual accurately admits deliberate impersonation, but the input is printed and predictable, so this is an ordinary capability of an agent controlling the session. **Smallest change:** say that the prompt records a confirmation but cannot establish human presence; require the agent to hand the exact action to the person outside its session. Present that residual explicitly for Randy’s written acceptance if the intended boundary remains terminal input alone.

**S2 — CARRIED F2; blocking; medium certainty. `REQ-002`, §3; `AT-007`, §6; helper 403–450 (helper/nats-local-setup.sh:403), 1093–1122 (helper/nats-local-setup.sh:1093).** A same-user process can replace a component after `chain_ok` and before a later pathname operation. The helper rechecks some paths and works relative to its current directory, but does not use directory handles for every operation as the contract expressly requires. The two swap tests do not prove the general invariant. **Smallest change:** either implement creation and destination writes relative to held, verified directory handles with no-follow behavior, or narrow the contract’s promise and state the remaining same-user race for written acceptance. Test replacement at creation, archive destination, and removal, asserting the replacement destination is untouched.

**S3 — CARRIED F5; blocking; high certainty. `REQ-002`, §3; `INV-003`, §5; helper 108–126 (helper/nats-local-setup.sh:108), 580–584 (helper/nats-local-setup.sh:580); test 566–723 (helper/nats-local-setup_test.sh:566).** If a subprocess emits a credential in an unrecognized form, its line can survive the pattern filter into terminal output or `server.log`. The persistent log does not pass through the helper’s `safe()` function, despite `REQ-002` saying it does. The tests prove filtering of their four chosen markers, not “no secret ever”; the OpenSSL-version assertion at line 723 always passes. **Smallest change:** avoid forwarding arbitrary subprocess text to persistent logs or receipts; emit fixed diagnostics or an explicit safe-field allowlist, and correct the test assertion. Specify which server-log fields may persist.

**S4 — CARRIED F6; blocking; high certainty about the contract reading. `REQ-010`, §3; `AT-007`, §6.** A parent starts an agent with `MASH_INSECURE_PLAINTEXT=1`. The agent’s later connecting command inherits it, prints the warning, and sends credentials and mail without encryption. That satisfies the current “inherited or not” words without a choice for this target and invocation. The supplied helper tests do not test mash’s network behavior. **Smallest change:** require a fresh, target-specific decision before network I/O, with a capture-server test that observes no credential bytes before it. If inherited opt-in is intentional, state that risk and obtain written acceptance.

**S5 — CARRIED F8; blocking; high certainty. `REQ-002`, §3; §8 “Release mechanics”; skill 356–375 (helper/2026-11-19-nats-local-skill-DRAFT4.md:356); guide test 143–158 (helper/mash-nats-local-guide_test.sh:143), 380–392 (helper/mash-nats-local-guide_test.sh:380).** The guide verifies files in one block and installs those pathnames in a later block. A process with access to the download directory can replace a file between them. The test’s 0.5.6 verifier is a shim that always accepts when the expected flags are present; it cannot reject a substituted or unsigned binary. **Smallest change:** combine verification and installation from an isolated private directory in one operation, verify the exact bytes installed, and add a test that substitutes the binary or attestation before verification and between verification and install. Record real 0.5.6 attestation verification when assets exist.

**S6 — NEW; blocking; high certainty. `REQ-009`, §3; §4 “Existing behavior to preserve”; skill 424–432 (helper/2026-11-19-nats-local-skill-DRAFT4.md:424).** An agent following the guide runs Alice and Bob with `MASH_GROUP` and `MASH_NAME`, while `REQ-009` explicitly removes both variables. The demo can select the wrong endpoint, fail, or appear to work only because old-form behavior survived contrary to the contract. **Smallest change:** change those guide commands to the full `MASH_ENDPOINT` setting, and run the guide test against an unpatched 0.5.6 build that rejects the removed variables.

**S7 — NEW; blocking; high certainty. `REQ-002`, §3; `INV-003`, §5; helper 351 (helper/nats-local-setup.sh:351), 1093–1129 (helper/nats-local-setup.sh:1093); skill 636–643 (helper/2026-11-19-nats-local-skill-DRAFT4.md:636).** The skill says not to run the helper as root, but the helper has no non-root check. If an agent invokes it with `sudo`, it creates root-owned signing keys and can start the network server as root. The contract promises files owned by “the user” but does not explicitly reject this path. **Smallest change:** make the helper refuse effective UID 0 before any creation and add a root-in-container refusal test; state that rule in `REQ-002`.

**S8 — CARRIED F7 and the server-binding gap; blocking; high certainty. `REQ-003`, §3; §5 “Custody of setup secrets”; `INV-003`, §5; `AT-007`, §6; §8 “Required evidence.”** The contract now says a live certificate must match the separately supplied CA and hostname **before writing anything**, but `AT-007` only substitutes both token server and CA while retaining the operator’s fingerprint. A faulty installer could pass that case yet accept an attacker-changed URL under the same CA, or write credentials before discovering a hostname mismatch. The existing acceptance list also never interrupts an atomic credential/config write. **Smallest change:** add a same-CA, substituted-address and hostname case, assert no file was written on failure, and interrupt each secret-write stage to check old files remain intact. Require those observations in the `AT-007` record.

**S9 — CARRIED F9; nonblocking; high certainty. §5 “Custody of setup secrets”; `REQ-002`, §3; helper 881–945 (helper/nats-local-setup.sh:881); skill 437–465 (helper/2026-11-19-nats-local-skill-DRAFT4.md:437).** `--retire-keys` removes the only local `ca.key`, `nsc/`, and `export/` after `tar -tzf` shows at least two entries. A truncated archive with two readable entries could satisfy that check while losing other signing material. The archive then remains on the server machine until a person moves it. **Smallest change:** compare required archive members and contents to each source before removal, require the guide to verify the off-machine copy, and test a partial archive failure with source files retained.

**S10 — NEW; nonblocking; high certainty. `REQ-002`, §3; §8 “Required evidence”; skill 437–465 (helper/2026-11-19-nats-local-skill-DRAFT4.md:437); guide test report (helper/2026-11-19-nats-local-skill-DRAFT4-test-report.md:1).** The supplied report says its copy-comparison block failed and proposes replacement text; the current skill contains that replacement. Thus the report’s 42 passed, 1 failed and 154 passed, 2 failed describe an earlier form, not a passing run of this exact skill. Its adopt success also used an uncommitted copy-behavior patch. **Smallest change:** rerun the current guide and unpatched implementation, retain the exact skill digest and result, and require all four custody comparisons to say `same`.

## Remaining gaps

- `REQ-003`, §3 does not say how the operator’s fingerprint **and intended server address** are delivered independently of the token. A hostname check against a CA proves certificate validity, but the person still needs to know which address they meant to trust.
- `INV-003`, §5 covers secret values in receipts, but §6 has no check that pathnames printed in diagnostics, commands, or test transcripts do not disclose sensitive directory or account information where that matters.
- `REQ-002`, §3 says the helper “writes nothing outside” its given directory, while its documented `--backup`, `--retire-keys`, and `--enable-boot` modes write an archive or user unit elsewhere. Name those mode-specific destinations and authority checks explicitly.
- §8 permits `go install ...@v0.5.6` and a marketplace plugin, but gives an installing agent no equivalent provenance check before running code from either route.
- The helper test runs rootless containers and exercises several real NATS flows, but its fake binaries, modified pins, patched adopt implementation, and attestation shim bound what its pass count can establish. The future `AT-007` run must identify substitutions per case.

## x-ops2 note on the custody model (mash-lead #835; the lane's judgment, not the reviewer's)

Question: is it acceptable that mashctl keeps the operator signing seed, the account identity seed and the system credentials in its own config directory after `adopt`, because it signs endpoints with them? My view: acceptable for a single-user local machine, with conditions; a design change if the machine or account is shared. I did not run anything; this rests on the contract and skill text the reviewer read.
- What the folder holds is signing authority for the whole NATS account: anyone who can read it can mint credentials for any identity and read every agent's mail (the system credential's reach), and later impersonate any endpoint. That is the same class as an SSH private key or a CA key on a developer machine, and the folder's readers are the OS account's processes and its backups. On a one-person local setup that is the existing OS-account boundary (the contract's own trust line for this setup), so keeping it is acceptable.
- Conditions: the folder 0700 and its files 0600, exclusive creation, checked at every use; excluded from backups and sync tools by the guide (not just "do not back up", name the common tools); mashctl never prints or logs the seeds; the guide says plainly what stays on the machine (operator seed, account seed, system credentials) and what goes off (the CA key and server key material, which sign and secure the server certificate only and cannot mint identities); the contract's section 5 lists the residual (an agent or process under the account can read the signing seeds) for Randy's written acceptance, not only in the skill.
- Design change needed if: the NATS server or mashctl runs on a shared host or an account other people or other agents' processes use, mash is used across machines, or "other machines too" is chosen: then signing should move to a separate admin account or machine, and the contract should say so rather than offer the same-account setup.
- Finding S9 (retire-keys deletes the only local copy after a weak archive check) matters more under this model: the signing seeds mashctl keeps are the only recoverable copy of the operator authority, so the archive and off-machine copy need a real verify before removal.
