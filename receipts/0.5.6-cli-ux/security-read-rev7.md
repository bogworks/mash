# Security read, mash 0.5.6 cli-ux revision 7 (draft)

Reviewer attestation: this security runs on model gpt-6-sol, Daybreak ON (codex -c daybreak=true), codex-cli 0.170.0, read-only sandbox.

I started with the rev 6 security read, then read the rev 7 contract’s credential and trust rules, authority rules, and network rules before checking the rest of the supplied workspace. This is a **text review**. I ran no helper, installer, binary, plugin, or acceptance test; the helper and skill DRAFT5 were not supplied. Rev 7 has no literal §5 credential table and no requirements named `NFR-002` or `NFR-003`; the operative text is chiefly `REQ-002`, `REQ-003`, `REQ-010`, `REQ-011`, `REQ-013`, `INV-003`, `INV-004`, `AT-007`, and §7.

## Threat model

The assets are signing seeds, administrator and endpoint credentials, TLS keys, stored mail, and the identity of the server a client trusts. An installing agent may have the user’s shell and terminal after a sparse request. Other processes under that user can read and replace user-owned files; other host users can connect to loopback TCP ports. The critical boundaries are the person’s choice versus an agent’s actions, owner-only files versus same-user processes, a downloaded artifact versus code executed or installed, and a token’s claims versus an independently established server identity.

## Findings

**F7-1 — CARRIED `F6-3`; blocking; high certainty. `REQ-003` and `REQ-013`, §3; `AT-007`, §6.** An implementer can follow `REQ-003` literally: offer install `--replace`, write `config.json`, `ca.pem`, and `trust.json` separately, then crash after the first rename. The next command may read mixed generations. `REQ-013` instead says install never mutates trust and `mash trust replace` is the only path. It does not specify whether credentials, config, CA, and `trust.json` all live behind the one pointer, or how a command obtains one generation consistently. A commit could also switch to a new account key while old endpoint credentials remain installed and unusable; `mash trust repair` only promises to discard a *half-written* version. **Smallest change:** delete `REQ-003`’s install `--replace` and multi-rename language. Define the complete pointer-selected generation, reader behavior, secret-file preconditions, post-commit validation, and recovery when the old key or server is unavailable. Make interruption tests assert the selected generation and usable credentials before and after each write and commit, with old bytes unchanged after refusal.

**F7-2 — CARRIED `F6-5`; blocking; medium certainty. `REQ-011(i)`, §3; §8 “Release mechanics.”** A compromised release page can supply a malicious script and a matching digest in its “attested notes.” The contract calls those notes an immutable artifact but does not say which attestation must authenticate the notes or what independently known identity binds their digest to this release. The script and its purported proof could therefore come from the same attacker-controlled origin. The attestation branch is substantially clearer; the alternate branch weakens it. **Smallest change:** require verification of the notes as a named attestation subject with the expected repository, workflow, and tag before using their digest, or remove the digest alternative. For the swap tests, require no executable installed on any failed verification and compare the installed files with the verified digests.

**F7-3 — CARRIED rev 6 authority gap; blocking; high certainty. `REQ-002` and `REQ-011`, §3; `INV-004`, §5; §7.** A user says “set mash up.” An agent chooses a release, runs downloaded setup code, chooses a local source directory, installs a plugin, and potentially chooses its permissions. `INV-004` requires a typed answer for trust or exposure changes but does not say which initial setup choices the agent may make under that sparse request. Its own terminal cannot establish the person’s choice; §7 `S1` recognizes this. There is no `NFR-002` in this draft. **Smallest change:** state the default agent authority for that request and name the choices that must come from the person’s separate channel: release provenance, `adopt --from` source, intended server address and CA fingerprint, plugin scope and permissions, and any widened listener, firewall, or startup scope. Require the skill to stop at those choices and test its behavior with a sparse request. Any retained ability for an agent to supply the confirmation itself needs explicit mash acceptance under `S1`.

**F7-4 — CARRIED rev 6 network gap; blocking; high certainty. `REQ-002` and `REQ-010`, §3; `AT-007`, §6; §7 `S4`.** A second host user can connect to a NATS port bound to `127.0.0.1`. Under the plaintext override, credentials and mail sent on that connection are unencrypted. `AT-007` now measures second-user reach, but the contract does not inventory every listening port, its authentication requirement, or which protocol data is exposed on a plaintext connection. There is no `NFR-003`. “Every local user can reach” a port means they can attempt a connection; it does not establish that they can read another connection’s payload without observation or interception capability. **Smallest change:** enumerate the helper’s listening ports and interfaces, authentication required on each, and the precise plaintext data exposed to the server and to processes able to observe or interpose on local traffic. Make the second-user test assert both reach and authorization outcomes per port. Keep `S4` as a separate written-acceptance item if inherited plaintext remains.

**F7-5 — CARRIED `F6-2`, `F6-4`, `F6-7`, and `F6-8`; blocking pending written acceptance; high certainty. `REQ-011(ii)` and `REQ-013`, §3; `INV-004`, §5; §7.** A same-user process can replace `trust.json`, config, and CA consistently, so the stated agreement check passes. It can also prepare a fully consistent `adopt --from` directory, or type a prompt through an agent-driven terminal. §7 accurately describes these risks and says homerange’s acceptance is precedent only. No mash-specific acceptance is recorded yet. The `REQ-013` “coordinated same-user replacement” test lacks an expected outcome: requiring refusal would promise a protection the design cannot provide. **Smallest change:** state that this test demonstrates the *limit* of the agreement check, not detection of a consistent replacement; state the expected result of the agent-prepared adoption test. Keep `S1`, `S2`, trust substitution, custody/adoption, and `S4` as distinct consequences for Randy to accept or reject in writing for mash. They share a same-user theme, but signing-seed custody and a pathname race are different capabilities; plaintext is separate.

**F7-6 — CARRIED `F6-4`; blocking; medium certainty. `REQ-011(ii)`, §3; `AT-007`, §6.** During `adopt --from`, a same-user process replaces a source pathname after its bytes are read, then restores it before a later path check. Held file handles and a copied-byte comparison protect the bytes actually read, but the words “a file replaced during the copy is detected and refused” promise more than those checks necessarily detect. The contract does not state whether the destination is committed atomically or what happens to partial copied files after refusal. **Smallest change:** define the check in terms of source inode and bytes read through held handles, compare destination bytes before commit, and specify destination cleanup or atomic commit on failure. Make the swap test assert which bytes, source, and destination were used. Keep a fully consistent same-user source as the custody residual; cryptographic checks within that directory cannot authenticate its origin.

**F7-7 — CARRIED `F6-6`; blocking; medium certainty. `REQ-011(iii)`, §3; `INV-004`, §5; `AT-007`, §6.** A verified mash binary can carry a plugin whose installation requests broad Claude Code permissions. The agent can run the user-scope local install under a sparse setup request, and the contract’s offline test would pass even if the plugin receives more authority than the person intended. “Refusing any other scope or destination” does not define the permitted permission set or verify the bytes actually installed. **Smallest change:** pin the plugin’s permission manifest and installed-byte digest to the verified binary, inspect the resulting destination, and require the person’s separate choice before any permission expansion. Test a substituted manifest and a destination with different bytes as refusals.

**F7-8 — NEW; nonblocking; high certainty. `REQ-002`, §3; §5 “Custody of setup secrets”; `AT-007`, §6.** The helper may create a key archive under `--backup` or `--retire-keys`; the contract checks archive contents before retirement but does not prescribe the archive’s initial mode, ownership, destination restrictions, or retention. An agent could put an otherwise complete archive in a shared directory, leaving signing material readable. **Smallest change:** apply `INV-003`’s exclusive 0600 creation and safe-parent rules to archives, name permitted destinations and deletion behavior, and inspect them in `AT-007`.

## Remaining gaps and acceptance boundary

The contract should add a literal credential inventory in §5 or point to one normative inventory. The table above exposes the missing server TLS key location and archive rules. It should also state the expected result for each adversarial test: in particular, coordinated same-user trust replacement is a demonstrated residual, while a mixed-generation read, substituted installed plugin, or failed artifact verification must refuse.

`REQ-003`’s trust-change wording should be reconciled with `REQ-013` before review: one still authorizes install `--replace` and asks for a fingerprint, while the other removes that flag and requires both address and fingerprint on first install. The latter supplies a sound first-use sequence **if** the separate operator channel is genuine: the person enters the intended address and CA fingerprint, TLS authenticates that host, and only then is the connected server’s account key used to verify the token. The token’s own claimed issuer alone is insufficient.

The §7 residual framing is appropriately mash-specific: Randy’s homerange decision does **not** accept any mash risk. Each listed residual needs its own written disposition before ratification if retained. In particular, `S1`, `S2`, coordinated trust replacement, custody including agent-prepared adoption, and `S4` should not be approved as one undifferentiated class.

## Summary

I find **7 blocking and 1 nonblocking findings** in revision 7. First-use identity and the log-retention issue are closed in contract text; replacement consistency, install provenance, agent authority, network exposure, adoption behavior, plugin permissions, and written acceptance remain blocking. My view is that revision 7 is **not ready for ratification** until the contract changes above are made or the retained risks receive Randy’s explicit mash-specific written acceptance. I verified text only and ran nothing.
