# Security read, mash 0.5.6 cli-ux revision 15 (draft)

Reviewer attestation: this security runs on model gpt-6-sol, Daybreak ON (codex -c daybreak=true), codex-cli 0.170.0, read-only sandbox.

I read the revision 15 contract (contract-0.5.6-cli-ux-rev15-draft.md), the revision 13 read (prior/security-read-rev13.md), the findings-by-origin sort (prior/security-findings-by-origin.md), and the supplied standards. I ran nothing. The helper, skill, release artifacts, target-output pages, and implementation were unavailable. The prompt’s `dev-process/`, `brief/`, ADRs, and `standing-orders/homerange.md` are absent from this workspace. This draft has no `NFR-002` or `NFR-003` IDs; their subjects are §5 **“Authority of an agent”** and **“Network exposure.”**

## Threat model

The assets are signing seeds, TLS keys, endpoint credentials, mail, and the choice of server trusted by an endpoint. An installing agent may act after only “set mash up.” Other host users can reach a loopback listener; processes with packet-capture rights can observe unencrypted loopback traffic. The critical boundaries are a person’s choice versus an agent’s choice, downloaded bytes versus verified bytes, an endpoint’s authority versus another endpoint’s mailbox, and owner-only files versus other OS users. Randy’s decision 264 expressly accepts what an agent or process running as the **same OS user** can do to that user’s files and terminal; I do not raise that standing risk as a finding.

## Findings

**F15-1 — NEW; blocking; high certainty. `REQ-003`, §3; `AT-002` and `AT-007`, §6; §5 “Authority of an agent.”** First install “SHOWS the person” an address and CA fingerprint and says to compare them with the operator’s separate message. An agent running the command can receive that output and continue without presenting it to a person; the acceptance tests check only that the values print. An attacker who supplies a token, address, and CA can therefore get its server installed during an unattended “set mash up” run. **Smallest change:** make the skill stop and hand the address and full fingerprint to the person for comparison with the operator’s separate channel, require the person’s answer before continuing the setup journey, and test that an agent with no answer stops. State explicitly that command output alone does not establish comparison. This is the reopened B2/R5-4/#840 concern identified in the origin sort, distinct from the accepted risk that a same-user agent could lie about a person’s answer.

**F15-2 — NEW; blocking; medium-high certainty. `REQ-003` and `REQ-011(ii)`, §3; `AT-007`, §6.** `--ca` is required and install checks the server certificate and host name against it before writing. Those checks establish that the server holds a certificate under the *supplied* CA for the *supplied* address. They do not state how the token’s signing authority is bound to that server. A coherent attacker-supplied token, CA, and server can pass the stated checks; even after an honest address and CA comparison, the requirement does not say that the JWT signature is checked against the account key served by that authenticated server. `REQ-011(ii)` names a credentials-signature check but does not identify the trusted source of its account key. **Smallest change:** require install and adopt to verify the token or credentials signature against the account key obtained from the authenticated server, and refuse any mismatch before writing. Test a valid JWT for a different account on a server with a valid certificate and host name. The token-names-no-server gap remains **open** until that binding and F15-1’s person comparison are explicit.

**F15-3 — CARRIED from `SR13-2`; blocking; high certainty. `REQ-002` and `REQ-011(i)`, §3; §8 “Release mechanics”; `AT-007`, §6.** Revision 15 removes the executable install script and says one offline `gh attestation verify --bundle` command checks the binaries, “naming this repository and its release workflow.” It does not specify where the bundle comes from, the expected tag and artifact subject, or a test that the verified subject is the exact bytes installed. An attacker controlling a download location could provide a different binary and a bundle for some valid attested artifact; an agent can also choose the expressly documented unverified `go install` route unless the setup authority excludes it. **Smallest change:** put the exact repository, workflow, tag, artifact subject, and subject-digest-to-installed-byte comparison in `REQ-011(i)`; identify how the bundle is acquired; require failure before installation on any mismatch. Make that verified route mandatory for an agent responding to a sparse setup request and test a substituted bundle, subject, and binary. The previous conflicting “reviewed guide digest” route is gone, but its supply-chain question has moved to the bundle command.

**F15-4 — CARRIED in substance from `SR13-5`; blocking; high certainty. §5 “Authority of an agent”; `REQ-011(iii)`, §3; §8 “Release mechanics.”** A sparse request authorizes an agent to install the marketplace plugin at user scope, while `REQ-011(iii)` calls it “not verified.” The draft gives no plugin identity, version or commit, manifest permissions, or limit on hooks and commands the agent may accept. A changed marketplace entry could gain broader file or command permissions during the authorized setup. This is a permission expansion through an external package, separate from decision 264’s acceptance of same-user file access. **Smallest change:** specify the exact plugin source and pinned revision plus the allowed manifest (MCP server, hooks, and permission entries); have the skill inspect and refuse any difference, or require the person’s own answer before installing the unverified plugin. Test a manifest with one added permission.

**F15-5 — NEW; blocking; medium-high certainty. `REQ-015`, §3; `AT-008`, §6.** The wake limit applies “while the backlog stays over the limit.” A sender able to deliver mail can send enough messages to cross the limit, wait for the session to show or drain them, then cross it again. The words permit an immediate wake on every crossing, even many times within ten minutes. The default wide-open mail policy makes an authorized but hostile endpoint a plausible sender. **Smallest change:** rate-limit wakes per destination endpoint across threshold crossings, with a ten-minute cooldown measured from the last wake; specify whether that cooldown survives a serve restart. Test repeated drain-and-refill cycles. The wake line contains a count, limit, and age—not mail contents—so the stated wake text itself does not disclose a message body.

**F15-6 — NEW; blocking; medium certainty. `REQ-003`, §3; `INV-003`, §5; `AT-007`, §6.** Install promises never to change an existing server, CA, or credentials file and to complete *each* new file atomically. It does not define a transaction across those files or a retry after interruption. A process killed after publishing config and CA but before credentials can leave a partial identity; the next run may refuse and tell an agent to move aside one file without saying which set must remain consistent. **Smallest change:** specify a preflight that refuses differences before any write, a staging/publication order or rollback rule for all install files, and an idempotent retry or explicit recovery for every interruption point. Test kills after each published file and verify that no partial state is usable or silently selected.

**F15-7 — CARRIED from the plain-text override finding; nonblocking; high certainty. `REQ-010`, §3; §5 “Network exposure”; `AT-007`, §6.** `MASH_DANGEROUSLY_SKIP_NATS_ENCRYPTION=1` is the sole stated route to plain text; the old variable and config key are removed. An inherited value still activates it without a new destination-specific choice. Every connecting command must warn on stderr before connecting, and status must show it. Against a server that accepts plain connections, a loopback packet-capture process can read credentials and mail; a TLS-only server refuses. **Smallest change if this is to be closed:** require a fresh choice for the specific destination rather than treating an inherited variable as sufficient. Randy’s §7 wording records his decision to rename the override and warn; it does not remove that transport consequence.

**F15-8 — NEW; nonblocking; medium certainty. `REQ-015` and `REQ-004`, §3; `INV-002`, §5.** `mash endpoint status` flags another endpoint’s over-limit mailbox “where it can tell,” but the draft does not define which identity performs that check or what count metadata it may read. An implementation could query mailbox counts using admin credentials and reveal another endpoint’s activity to an ordinary endpoint-status caller. **Smallest change:** constrain the check to mailboxes visible to the caller’s endpoint credentials and owner scope; if the check cannot be authorized, show unknown rather than querying with admin authority. Test a different owner and an unauthenticated caller. No text authorizes reading another mailbox’s message bodies to calculate the count.

**F15-9 — CARRIED clarification from `SR13-4`; nonblocking; high certainty. `REQ-003`, §3; §5 “Security, reliability, compatibility, performance”; `AT-007`, §6.** Missing `--ca` must refuse “before reading anything,” while deciding and reporting the install state can require reading local metadata. Also, §5 still says `credential install` writes “config and trust” although `REQ-013` removes the trust record. **Smallest change:** say refusal occurs before reading the supplied key, token, or CA, connecting, or writing; remove “and trust.” The test should assert those concrete effects.

## Credential and transport inventory

`INV-001` and `INV-003`, §5, prohibit seed, JWT, and key **values** in argv, text, JSON, logs, errors, examples, and receipts. `AT-007` adds a scan and permits failure-path file paths in receipts only from scratch homes. Mode 0600 excludes other OS users; it does not exclude processes running as the owner, which decision 264 accepts.

| §5 credential row | Location, readers, agent action, and exposure |
|---|---|
| Operator signing seed, account seed, system credentials | Mashctl config directory, 0600; mashctl and the owner’s processes can read them. They permit minting identities and reading all mail. Sparse setup authorizes adoption, which copies needed material, but not export or disclosure. Values must stay out of argv, logs, and receipts. |
| Admin credentials | Mashctl config directory, 0600; mashctl and the owner’s processes can manage endpoints and buckets. No value may appear in argv, logs, or receipts. `mashctl status --detail` may show the **path**. |
| CA key | Helper directory, 0600; the owner’s processes can mint server certificates. The helper may create it; no backup, export, or retirement mode is authorized in 0.5.6. No value may enter diagnostics or receipts. |
| Server TLS key | Helper server directory, 0600; nats-server and the owner’s processes can impersonate the server if it leaks. The helper may create and use it; no value may enter output or logs. |
| CA certificate | Server directory and mash config, 0644; everyone can read it. It is public trust material, not a secret. The `--ca` **path** may appear in argv; the fingerprint and address require the separate comparison in F15-1. |
| Endpoint seed key | Endpoint machine, 0600; mash and the owner’s processes can act as that endpoint. `--key` exposes its path, never its value. An agent may create it for a person-named endpoint, not transmit its private contents. |
| Endpoint credentials | Mash config directory, 0600; mash and the owner’s processes can act as that endpoint. Install or same-user create may write them; `--creds-out` exposes a destination path. Values must stay out of argv, logs, and receipts. |
| Token (JWT) | Person-carried operator file, 0600; install reads it in place, and the person deletes it afterward. `--token` exposes its path. The token value must not appear in argv, logs, or receipts; combined with its key, it permits acting as the endpoint. |

The §5 network rule permits one TLS NATS client listener on `127.0.0.1` by default. Any host user can attempt a TCP connection, but credentials are required and TLS protects payloads from other connections. Monitoring, cluster, gateway, and leaf-node ports are excluded by default. The plaintext override permits an observer with packet-capture rights on loopback to read credentials and mail; the warning precedes the connection. The contract does not claim that loopback itself is private.

## Gaps to state in the contract

- `REQ-015` should name the identity and permission used to count backlog, whether it reads metadata only, and the exact scope and failure value for other endpoints’ status. It should say that unauthenticated senders cannot create backlog through the helper’s authenticated NATS listener; authorized senders can still consume mailbox capacity.
- `REQ-011(i)` should state that the agent cannot substitute `go install`, a neighboring `SHA256SUMS`, or a marketplace asset for the verified release-binary path during a sparse setup.
- `REQ-003` should define recovery from interrupted installation and from a refusal naming a file to move aside, without implying that moving one member of a partial set is safe.
- `REQ-002` should resolve its own phrase “write nothing outside its directory” against downloading/installing mash and mashctl into `~/.local/bin`: state whether that installation belongs to the helper or to the separate `REQ-011(i)` step.
- §5 “Network exposure” should say whether the operator-provided server path may expose additional NATS ports; the helper’s one-port guarantee does not constrain a server the operator already runs.

## Summary

I find **six blocking** findings and **three nonblocking** findings in the revision 15 text. In my view, F15-1 through F15-6 block ratification until resolved or expressly accepted by the ratifier under the contract standard. Decision 264 already disposes of the same-OS-user standing risk; this read does not reopen it. These are findings about requirements only: I read text and ran no code or tests, and could not verify the unlanded helper, skill, release checks, or runtime mailbox behavior.
