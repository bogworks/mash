# Security read, mash 0.5.6 cli-ux revision 5 (draft)

Reviewer attestation: this security runs on model gpt-6-sol, Daybreak ON (codex -c daybreak=true), codex-cli 0.170.0, read-only sandbox.

I read the supplied workspace text and ran nothing. The DRAFT5 helper and skill are not present, so every judgment below is about the contract’s requirements and proposed tests, not their implementation. This draft has no literal section 5 credential table or `NFR-002`/`NFR-003`; the relevant provisions are `REQ-002`, `REQ-003`, `REQ-010`, `INV-001` through `INV-004`, and §5 “Custody of setup secrets.”

## Threat model

The assets are account signing authority, endpoint credentials, TLS private keys, stored mail, and the server identity clients trust. An installing agent may control a shell and its terminal while acting on a sparse instruction such as “set this up.” Processes under the same OS user can read or change that user’s files; other host users can connect to a loopback TCP port. The critical boundaries are between the person and the agent, an owner’s directory and an attacker-chosen directory, downloaded artifacts and executed code, and a token’s claims and independently authenticated server identity.

## Revision 4 disposition

“Closed” means revision 5 now states a requirement and a meaningful acceptance check. It does **not** mean the absent DRAFT5 helper, skill, or future release passed.

The remaining terminal boundary cannot prove human presence. |

No new requirement checks sensitive path disclosure in receipts; `INV-003`, §5 protects secret **values**.

## Credential and trust inventory

| Material | Residence and readers | Agent authority and exposure required by the draft |
|---|---|---|
| CA private key and server private key | Helper’s 0700 directory initially; its owner’s processes and privileged processes can read them. §5 says the CA key later moves off-machine; the server retains the key needed for TLS. | `REQ-002`, §3 lets an agent run the helper. `INV-003`, §5 bars secret values in argv, logs, JSON, errors, and receipts. The contract must identify the server-key destination and reader after setup. |
| Operator and account signing seeds | Helper exports initially; copies needed by mashctl in its 0700 configuration directory with 0600 files, per `REQ-002`, §3 and §5 “Custody of setup secrets.” Same-user processes can read them. | The holder can mint identities; §5 says the holder can read every agent’s mail. The agent may run adoption using paths, but must not pass seed values in argv or print them. Backup and sync exclusion is required in the guide, not demonstrated here. |
| System and admin credentials | Helper exports and mashctl’s private configuration after adoption. Same-user and privileged processes can read copies. | `mashctl adopt --from <dir>` copies them under `REQ-011`, §3. `INV-003`, §5 forbids credential values in command lines, output, logs, and receipts. The contract does not yet constrain which source directory that command may trust. |
| Endpoint private key, token, and installed `.creds` | The key and token arrive as files or stdin; installed credentials reside in the current user’s mash configuration, 0600, under `REQ-003` and `INV-003`. | An agent may pass **paths** to `mash credential install`. Token, seed, and key values may not appear in argv or receipts. Existing credentials are refused rather than overwritten. A file path can still disclose account or location information. |
| Account public key, CA certificate, fingerprint, server URL | CA and URL become config trust inputs. The proposed account-key pin is **not in revision 5’s text**; it therefore has no specified residence, protection, or mutation rule. | `REQ-003`, §3 requires a separately supplied fingerprint and address on first CA installation, and §5 requires a live CA and hostname check. An agent controlling the terminal can enter known confirmation text. |
| Logs, archives, test records | Persistent server log, optional retirement or backup archive, command output, and acceptance receipts. Archives intentionally contain secrets. | `REQ-002`, §3 requires safe log fields and archive-content comparison. `INV-003`, §5 prohibits secret values in receipts. The archive’s destination, readers, and verified off-machine transfer need to appear in the guide and evidence. |

`REQ-002`, §3 correctly says **other users on the same host can reach** the default `127.0.0.1` listener. They can contact the TCP/TLS and NATS authentication surface; loopback binding does not make it private to the installing user. TLS and valid credentials are intended to restrict account access. Under `REQ-010`, §3, the plaintext override instead sends credentials and mail over that local connection unencrypted; the warning does not restrict which local process can observe or interfere with traffic.

## Findings

**R5-1 — CARRIED S1; blocking; high certainty. `INV-004`, §5; `AT-007`, §6.** An agent opens a PTY, reads the requested address or fingerprint, and types it back. Revision 5 itself says a test can do this, yet `INV-004` still says the prompt “stops an agent acting without” a person. That conclusion does not follow from terminal input. **Smallest change:** describe the prompt as a recorded confirmation, require the guide to hand the exact change to the person outside the agent-controlled session, and make §7’s acceptance say plainly that an agent able to drive the terminal can impersonate the person. A reviewer can test refusal without a terminal and correct input through an agent PTY; no local test can prove who typed it. **If retained, Randy’s specific written acceptance is needed.**

**R5-2 — CARRIED S2; blocking; medium certainty. `REQ-002`, §3; `AT-007`, §6; §7 “Residual risks.”** A same-user process swaps a checked pathname before creation, archive writing, or removal. Inode rechecks can miss a later substitution; a write may go to a different directory or removal may affect different files. Revision 5 acknowledges “a race” but does not say what the race permits. **Smallest change:** specify the operations and destinations still exposed, test swaps at all three named stages with the unintended destination untouched, and present the bounded outcome for written acceptance—or require held directory handles and no-follow operations. **A remaining redirect or removal risk needs Randy’s specific written acceptance.**

**R5-3 — CARRIED S4; blocking; high certainty. `REQ-010`, §3; `AT-007`, §6; §7 “Residual risks.”** A parent launches an agent with `MASH_INSECURE_PLAINTEXT=1`; a later agent command inherits it and sends credentials and mail unencrypted after printing the required warning. The contract expressly allows “inherited or not” and tests only warning behavior. **Smallest change:** require a fresh decision tied to the destination before connecting, and test with a capture server that no credential bytes leave before that decision. If inherited opt-in remains intentional, §7 must say that any parent of the agent can authorize plaintext for later commands without a fresh user action. **That behavior needs Randy’s specific written acceptance.**

**R5-4 — NEW, account and server binding; blocking; high certainty. `REQ-003`, §3; §5 “Custody of setup secrets”; `AT-007`, §6.** Revision 5 contains **no requirement** for the proposed account-public-key pin or JWT issuer check. With an existing server and CA, an installer may accept a token from another account while reusing the saved trust configuration; “with no CA involved it asks nothing.” Even the proposed issuer check only establishes that the token names the recorded account key if the signature is verified. It does not prove which server owns that key, protect a first install with no recorded key, or handle account-key rotation. A same-user process able to edit `config.json` can substitute the pin; reuse of one account key across servers defeats a key-only server binding. **Smallest change:** add a requirement that first installation binds a cryptographically verified token issuer, independently confirmed server address, and CA fingerprint as one protected trust record; later installation verifies the JWT signature and issuer against that record and refuses mismatches without changing files. Specify where the key lives, who may replace it, a separate confirmed rotation path, and a refusal that tells the person to obtain the correct token or perform that rotation. Test different-account tokens on one server, same-account-key reuse on another server, altered config, first-install substitution, and rotation.

**R5-5 — NEW, `adopt --from` source trust; blocking; high certainty. `REQ-011`, §3; `REQ-002`, §3; `INV-003`, §5.** The proposed fingerprint-free local adoption is **not stated** in revision 5; `REQ-011` only says to copy from `<dir>`. An agent can create a directory containing its own CA and signing material, point `--from` there, and have mashctl adopt it as the operator’s setup. A directory the person was told to use can also be prepared or changed by an attacker before adoption. **The no-fingerprint route is acceptable only as a same-owner local copy, not as independent authentication:** require the source directory and every parent to pass ownership, mode, and symlink checks; read the CA, account public key, and corresponding credentials from the same verified directory; cryptographically check their relationship; hold directory handles and reject file replacement during copying; reject an already-adopted trust record unless an explicit person-confirmed replacement path is taken. The output must say that no fingerprint was requested because trust came from that owner-controlled directory, and that the directory’s contents were not independently authenticated. Test a symlink, writable parent, mixed CA/account files, source-file swap during copy, rerun with changed contents, and an agent-prepared source. A same-user attacker who can prepare the person’s source directory remains within the custody residual and must be stated for acceptance if this design is kept.

**R5-6 — NEW, release install script provenance; blocking; high certainty. `REQ-011`, §3; `REQ-002`, §3; §8 “Release mechanics.”** A page may download, “check,” and run an attested script, but the contract does not identify the exact origin, tag, attestation identity, digest, or check command for the **script itself**. An attacker replacing the script and a beside-it checksum can cause execution before any binary verification. “One command installs” also leaves sudo use, install destinations, ownership, and failure cleanup undefined. **Smallest change:** pin the script and both binaries to the exact 0.5.6 release identity; require independent attestation verification or a digest embedded in reviewed material before script execution; verify each binary’s exact bytes before installation; state that the agent shows the command and source first, never pipes into a shell, does not invoke sudo or change a system directory on its own, and reports all destinations. Test script substitution, binary substitution, a verification-to-install swap, and no writes after failed verification. The `go install ...@v0.5.6` developer route remains explicitly unverified and must not be offered as the agent’s verified quick start.

**R5-7 — NEW, plugin installation authority; blocking; high certainty. `REQ-011`, §3; §8 “Release mechanics”; `INV-004`, §5.** `mash plugin install` may export, add, and install a Claude Code plugin in one command, but the contract gives no source, exact version or digest, permission scope, destination, or verification rule. A compromised marketplace entry or changed plugin can gain code execution in the agent environment; the command could also alter another user’s or global configuration if run with wider permissions. **Smallest change:** name the pinned plugin source and release identity, verify the downloaded bytes before execution, limit writes to the invoking user’s Claude Code configuration, forbid implicit sudo/global install, print the commands and destinations, and require the person’s confirmation for any permission or scope expansion. Test a substituted plugin, changed pin, and attempted global destination. Listing “the plugin route” as unverified in `REQ-002` conflicts with making it the quick-start route in `REQ-011`; resolve which assurance the quick start promises.

**R5-8 — CARRIED S6; nonblocking; medium certainty. `REQ-009`, §3; `REQ-008`, §3; `AT-001`, §6.** A guide can still tell Alice and Bob to set removed `MASH_GROUP` and `MASH_NAME`; the journey may work only because obsolete behavior accidentally survives. The absent DRAFT5 skill prevents checking its actual commands. **Smallest change:** make `AT-001` run the exact published guide with only `MASH_ENDPOINT` or the documented automatic choice, and fail if any guide command or environment contains either removed variable.

**R5-9 — NEW, conflicting credential-write rules; blocking; medium certainty. `REQ-003`, §3; `INV-003`, §5; `AT-007`, §6.** `REQ-003` says a changed server or CA needs `--replace` and an atomic “verified pair,” while `INV-003` says an existing different secret file is “never … replaced,” and `REQ-003` says existing credentials are “never overwritten.” An implementer could update `config.json` after consent while retaining an old credential, creating a trusted server/credential mismatch, or refuse a necessary paired update after partially writing configuration. **Smallest change:** define the transaction precisely: which existing files may change on `--replace`, which must be moved aside by the person, the order of validation and commit, and the unchanged state after every refusal or interruption. Test each interruption point and compare both files with their originals.

## Four proposed written residuals

| §7 residual | Is it precise enough to accept? |
|---|---|
| S1 | **Partly.** It admits agent-driven terminal input but still suggests the prompt stops ordinary agent action. State that any agent with terminal control can supply the confirmation and what the external handoff does and cannot enforce. |
| S2 | **No.** “Could race them” omits the possible redirected write, archive, or removal and the affected destinations. |
| S4 | **Partly.** It names inherited plaintext but should say that a parent can cause subsequent agent commands to send credentials and mail unencrypted without a fresh choice. |
| Custody | **Partly.** It identifies same-user readers; add the authority gained—mint any identity and read every agent’s mail—and that 0700/0600 does not exclude same-user processes or their backups. |

If R5-5’s fingerprint-free adoption retains a source directory that an agent or same-user process can prepare, that specific reliance on local directory custody also belongs on the written-acceptance list. If the release intentionally keeps the unverified plugin route in the agent quick start, its code-execution and permission scope need an explicit acceptance; the present wording is too thin for that choice.

## Other gaps to state

- `REQ-011`, §3 does not say whether `--from` refuses a changed source on rerun, whether it can replace existing account trust, or how it prevents a file-copy race.
- The proposed account-public-key design has no requirement or `AT-007` test at all. The token’s issuer, the recorded account key, the server address, and the CA must be treated as distinct claims and bound together explicitly.
- `REQ-002`, §3 requires a running log free of secrets but does not define retention or access mode for `server.log`; `AT-007` should record its reader permissions as well as canary absence.
- `INV-003`, §5 forbids secret **values** in receipts but does not bound disclosure through printed read paths. Its acceptance scan should include the exact command, diagnostic, and receipt forms used by the guides.
- `REQ-011`, §3 makes an agent-run installation path central to the quick start without saying what the agent may change under the user’s brief instruction, particularly for plugin permissions and system-wide writes.

## Summary

I find **7 blocking and 1 nonblocking carried/new security issues plus one blocking consistency issue**: **8 blocking and 1 nonblocking findings** in total. R5-1 through R5-7 and R5-9 block ratification in my view unless fixed or specifically accepted in writing under `contract/STANDARD.md`; the four proposed residuals need sharper descriptions before they can serve as that acceptance. The account-key and fingerprint-free adoption proposals are not yet requirements in revision 5, so their protection cannot be credited. I verified contract text only and ran no installer, helper, binary, plugin, or acceptance test.
