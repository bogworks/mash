# mash releases (G19): v0.1.0 as a tagged, reproducible build (revision 2)

**Why:** A downstream consumer pinned mash by a bare commit (`dd2f033`) because mash has no tagged releases (G19). This gives mash
`v0.1.x` tags with a release gate of its own, so a downstream consumer can pin a tag and its commit.
**Model:** A downstream consumer's release pipeline (private, not in this repo), ported, not re-invented: `internal/release` (`build.go`: sanitized build
environment, `CheckSource`, release flags; `checks.go`: CI eligibility), `scripts/buildrelease`,
`scripts/releasecheck` + `scripts/release-check`, `.github/workflows/release.yml`. Reduced: mash has no live
receipt, review file or scenario manifest. The maintainer pushes the signed tag and publishes; nothing here tags.
**Revision 2** answers Codex's review of revision 1 (8 findings, the High ones all "the port was a weaker gate").

## Decisions

1. **Version.** `endpoint.Version` defaults to `"dev"`. `mash version` prints `mash <version> (commit <sha>)`;
   `<version>` is, in order: the release ldflag `-X github.com/bogworks/mash/internal/endpoint.Version=<v>` (any
   value but `dev`), else the module version of a `go install …@v0.1.0` build (`debug.ReadBuildInfo`
   `Main.Version` minus `v`; `(devel)` and empty are ignored), else `dev`. `main` resolves it **before command
   dispatch** and stores it in `endpoint.Version`, so the SAP service version is the same string (tested).
2. **Build recipe** =  the downstream pipeline's `buildEnv`/`Build`: every `GO*`/`CGO_*` variable that could change the output is
   dropped (`GOFLAGS`, `GOROOT`, `GOEXPERIMENT`, `GOAMD64`…, a go env file, a workspace); pinned
   `GOTOOLCHAIN=go1.27.3 GOENV=off GOWORK=off GOFLAGS= CGO_ENABLED=0`; flags `-trimpath -buildvcs=false -mod=readonly`
   and `-ldflags "-X …endpoint.Version=<v> -X main.commit=<sha>"`; no build tags. `CheckSource` refuses a tree
   whose `HEAD` is not the full 40-hex commit, that is dirty, or that holds the output.
3. **`release-check <X> <version>`** judges candidate X: X is a full sha and an ancestor of `main` **fetched from the
   release repository** (`bogworks/mash`, never a configured origin) into a dedicated ref, failing closed;
   version is `N.N.N`; the CI check runs `test (ubuntu-latest)`, `test (macos-latest)`, `reproducible` on **X**
   (every page; latest run per name; all `completed`/`success`; wrong sha, duplicate ids and truncated listings
   refused), read through `gh api`; X is built from **fresh clones in two different directories** (with a hostile
   ambient Go environment scrubbed) and the hashes must match; the binary prints exactly `mash <version> (commit X)`.
   It reports every problem; exit 0 passed, 3 refused, 4 the gate could not decide, 2 usage. There is **no
   `--no-ci` bypass**.
4. **`release-check --assets <version> <X>`** runs after CI drafted the release: the remote tag `v<version>` exists,
   is **annotated**, **peels to X**, and `git verify-tag` accepts its signature with this machine's keys (the exact
   listed object is fetched, and re-listed afterwards: a moved tag fails); the release has **exactly** the four
   binaries (`mash-{linux,darwin}-{amd64,arm64}`) and `SHA256SUMS`, no more; each binary's digest equals the
   SHA-256 of **our own fresh build of X for that target**, and `SHA256SUMS` lists those four lines exactly.
5. **`release.yml`** on tag `v*`: the tag name must match `^v[0-9]+\.[0-9]+\.[0-9]+$`; annotated + signature
   shape; X on main; per target two fresh-clone builds with `scripts/buildrelease` that must match; upload; a
   `draft` job writes `SHA256SUMS` and a changelog (`git log` since the previous tag) and creates a **draft**
   release (`contents: write` only there). `ci.yml` gains a `reproducible` job (two fresh-clone builds of the
   pushed commit) and its check name is the one `release-check` requires.
6. `docs/release.md` is the procedure (check, tag, CI, `--assets`, publish, an optional pin by a downstream consumer).

## Tasks (test-first; Codex on the plan and on each diff)

1. **Version resolution** (`cmd/mash`): table test of precedence (ldflag, module, `(devel)`, empty, `dev`); a built
   binary prints the ldflag form; the SAP service version equals it.
2. **`internal/release` build** (ported tests): the same source built in two directories, with a hostile ambient Go
   environment (`GOFLAGS=-tags=x`, `GOEXPERIMENT`, `GOAMD64`, `GOWORK`, `GOENV`) and different `GOCACHE`/`GOMODCACHE`
   gives identical bytes; `CheckSource` refuses a wrong HEAD, a short or uppercase sha, a dirty tree, an output in
   the tree; a different **commit** (a real second commit) gives different bytes; the version line is exact.
3. **`internal/release` CI + assets**: `CheckCI` tables (stale success then failure, missing, pending, wrong sha,
   duplicate ids); `CheckAssets` (missing, extra, misnamed, substituted digest, bad `SHA256SUMS`).
4. **`scripts/buildrelease`, `scripts/releasecheck`, `scripts/release-check`**: driven against a throwaway repo and a
   fake `gh` (as the downstream pipeline's tests are): not on main, stale main, fork as origin, malformed version, CI failures and
   API errors (exit 4), truncated listings, two-build mismatch, a signed tag test with a generated key, a lightweight
   tag, a tag on another commit, a tag moved between list and fetch, extra/missing/substituted assets.
5. **Workflows** (`release.yml`, `ci.yml`): a test parses both and asserts pins and guards (as the downstream pipeline's
   `workflows_test.go`), and runs the tag-name guard script against good and malformed names.
6. **Docs and dry run**: `docs/release.md`, README install note; `release-check` run for real at HEAD up to the
   parts that need a tag (reported to the maintainer, who tags).

## Review Focus

Reproducibility leaks; the gate trusting a tag name instead of the commit; forged/lightweight/moved tags; CI
eligibility by name only; a downstream pin on a commit other than the tag's; the draft job publishing without the gate.
