### Summary

**mash 0.5.8 exists for a fleet migration: it lets mash accept keys that another tool issued, which you list in `config.json` under `external_keys`, so `mashctl doctor` no longer fails on them ([#1300](https://github.com/bogworks/mash/issues/1300)), and `install.sh` tells you how to fix a folder it refuses ([#1240](https://github.com/bogworks/mash/issues/1240)).** If your NATS account is shared with other tools, list their user public keys as `external_keys` in `config.json` and the `keys` check passes; if you never share an account, nothing changes. The rest is smaller: one count for `mash inbox` and the idle wake, a refused-mail count that is repaired after a kill, safer installer and setup scripts, and a bigger default for the local server. Every download has a build attestation; verify it. The known issues are listed in the release notes.

### Upgrading

Update both plugins, `mash` and `mash-setup`, then restart your Claude Code sessions: the serve and inbox fixes need a restart.

### Upgrading in detail

Two things you may want to do:

1. **If your NATS account is shared with other tools,** add `external_keys` to `config.json`: an array of the exact user public keys (`U...`) those tools use. Then run `mashctl doctor`; a listed key that is connected no longer fails the `keys` check. Leave it out and nothing changes.
2. **If you set up a local server before 0.5.8,** it keeps its old limits of 64 streams and 128 consumers. The new default of 1024 applies to servers set up with 0.5.8. Tested steps for raising the limits of an existing server are tracked in [#1301](https://github.com/bogworks/mash/issues/1301).

### What changed

#### Added

- **`external_keys`, an optional `config.json` setting.** `mashctl doctor` checks that every key connected to your account was issued by mash. On an account shared with other tools it used to fail on every key mash did not issue. List those keys here and a connected one is accepted; the line then reads `every connected key was issued here or listed (1 external)`. A key that is neither issued here nor listed still fails, and the failure says to list it or revoke it. A bad entry (one that is not a user public key, has whitespace around it, or repeats an earlier one) is not just a `mashctl doctor` setting: it stops every mash command that reads the configuration, including mail, until you fix or remove it. The error names the entry (a seed is never echoed). A key mash issued and revoked still fails even when listed. Tracked at [#1300](https://github.com/bogworks/mash/issues/1300); the decision is [ADR 0165](https://github.com/bogworks/mash/blob/v0.5.8/docs/decisions/0165-doctor-takes-keys-issued-elsewhere-from-an-external-keys-allowlist-in-config-json.md).

#### Changed

- **`install.sh` names the fix when it refuses a folder.** Claude Code's own installer leaves `~/.local` and `~/.local/bin` writable by their group, and `install.sh` refuses such a folder. It used to stop without saying how to go on. The message now names the folder and the command, `chmod go-w <folder>`, and you run the installer again. It names one bad folder per run, so you may need to run it more than once; the common case is `~/.local` and `~/.local/bin`. What it accepts does not change ([#1240](https://github.com/bogworks/mash/issues/1240)).
- **`mash inbox` and the idle wake count waiting mail one way.** One pass over the waiting messages gives the total, new, urgent and oldest-waiting numbers, so the urgent count covers the waiting backlog (up to 1000 messages), not the newest 200 messages, and an older message from a deleted sender is no longer counted. The pass is capped at 1000 messages or 32 MiB. The output text does not change ([#955](https://github.com/bogworks/mash/issues/955), [#1054](https://github.com/bogworks/mash/issues/1054)).
- **The local server setup allows 1024 streams and 1024 consumers.** `mash-local-nats-setup.sh` gave the account 64 streams and 128 consumers, so a server ran out of room after a few dozen endpoints. The disk limit stays at 2 GiB and is now the one you reach first, at about 122 endpoints ([#1253](https://github.com/bogworks/mash/issues/1253)).

#### Fixed

- **An interrupted `install.sh` no longer splits the two programs.** Ctrl-C, a closed terminal or `kill` while it replaces `mash` and `mashctl` now leaves both old or both new. `kill -9` cannot be caught and can still split them ([#1071](https://github.com/bogworks/mash/issues/1071)).
- **`mash-local-nats-setup.sh --start` checks that a running server answers.** It used to say "already running" whenever the recorded process was alive. Now, if the server does not answer, it exits with an error and tells you to run `--stop`, then `--start`; it changes nothing itself ([#1094](https://github.com/bogworks/mash/issues/1094)).
- **Only one run can take over a stale lock in `mash-local-nats-setup.sh`.** After a killed run, two runs started at once could both start, stop or remove the same server. One now reports busy, and a lock left by a run killed mid-takeover is named so you can remove that one file ([#1093](https://github.com/bogworks/mash/issues/1093)).
- **`mash-migrate-0.5.5.sh` works only inside the mash folder it entered.** A parent folder replaced while it runs can no longer redirect what it reads or writes, and the backup holds exactly the `config.json` it checked ([#1063](https://github.com/bogworks/mash/issues/1063)).
- **`mash doctor`'s refused-mail count is repaired after a kill.** If `mash serve` was killed between recording a refused message and updating the count, the count stayed one low. It is now repaired the next time that message is handled ([#1069](https://github.com/bogworks/mash/issues/1069)).

### Verify your download

Every download has a build attestation; verify it before you run it, with the steps in [Verify what you download](https://github.com/bogworks/mash/blob/v0.5.8/docs/install.md#verify-what-you-download) and [Verify a release](https://github.com/bogworks/mash/blob/v0.5.8/docs/release.md#verify-a-release).

### Known issues

There are 54 known issues. They are the 0.5.7 known issues that are still open, and the ones found since. Each has an issue; the issue is the place for detail and any workaround. Listed by what you would notice.

Mail and trust:

- [#874](https://github.com/bogworks/mash/issues/874): refused unverified mail: the sender is not told, and the mail is still stored.
- [#935](https://github.com/bogworks/mash/issues/935): an administrator cannot see which messages an endpoint refused.
- [#958](https://github.com/bogworks/mash/issues/958): `mash inbox` may count unverified mail that `serve` has not yet refused.
- [#990](https://github.com/bogworks/mash/issues/990): `mash read` at a shell can say "refused" for mail `serve` delivered under `--accept-unverified`.
- [#960](https://github.com/bogworks/mash/issues/960): a signed message replayed within 5 minutes shows as verified a second time (no workaround).
- [#883](https://github.com/bogworks/mash/issues/883): `Mash-Kind` is unsigned.
- [#866](https://github.com/bogworks/mash/issues/866): `mash read` from a shell with no session does not tell the server until the next session starts.
- [#1070](https://github.com/bogworks/mash/issues/1070): `mash inbox` gets slower with the span of the mailbox's messages, not the size of the page.
- [#918](https://github.com/bogworks/mash/issues/918): `mashctl`'s online (holds the lease) and `mash who`'s online (heartbeat) can disagree for up to 90 seconds.
- [#1039](https://github.com/bogworks/mash/issues/1039): mash cannot discover endpoints served by a SAP SDK host.

Setting up and installing:

- [#878](https://github.com/bogworks/mash/issues/878): one config folder serves one mesh; a second mesh needs `--config-dir`.
- [#965](https://github.com/bogworks/mash/issues/965): `mashctl init --config` refuses a folder set up for a different server.
- [#1341](https://github.com/bogworks/mash/issues/1341): on macOS, `mash-local-nats-setup.sh` refuses `--dir` under `/tmp`, and its hint `chmod go-w /tmp` is wrong: do not follow it. Pick a folder under your home instead; the default, `~/mash-nats`, works.
- [#1344](https://github.com/bogworks/mash/issues/1344): a bad `external_keys` entry in `config.json` stops every `mash` command, mail included. Fix or remove the entry.
- [#1345](https://github.com/bogworks/mash/issues/1345): the hint `mashctl doctor` gives for a bad `external_keys` entry (`mashctl init --config`) does not fix it. Edit `config.json` as the detail line says.
- [#1065](https://github.com/bogworks/mash/issues/1065): `mashctl init` prints an unknown setup key in its error.
- [#865](https://github.com/bogworks/mash/issues/865): the NATS helper has no boot start, upgrade, backup, other-machine listening or key retirement.
- [#995](https://github.com/bogworks/mash/issues/995): `mash-local-nats-setup.sh --remove` refuses when a later instance took a stopped folder's recorded port.
- [#1099](https://github.com/bogworks/mash/issues/1099): a failing `mash doctor` ends `1 problem.` with no fix, though its help says it tells you how to fix what is wrong, and some hints point at a command that gives the same answer: `mash status` hints `mash doctor`, and `mashctl doctor` on a down server hints `mashctl status`, which only checks. Anyone who follows the hints after a failure meets this, and an agent that follows every hint can loop. No workaround to run; read the failing row itself, which names the fault. For a local server that is down, the fix is `mash-local-nats-setup.sh --start`, which neither command prints.
- [#959](https://github.com/bogworks/mash/issues/959): `install.sh` checks checksums only when `gh` is missing or too old; the one-line commands run a script before you can read it.
- [#1153](https://github.com/bogworks/mash/issues/1153): gh 2.48 to 2.67 has `gh attestation` but no `--source-ref`, so `install.sh` stops with "the attestation of the release's SHA256SUMS did not verify: nothing was installed". The message wrongly blames the release. Workaround: use gh 2.68.0 or later, or take gh off PATH.
- [#1231](https://github.com/bogworks/mash/issues/1231): on a personal Claude account, `--channels plugin:mash@mash` alone does not load mash's channel, so an idle session is not woken; the wake needs `--dangerously-load-development-channels plugin:mash@mash`, with Claude Code's warning screen at every start, and in a Team or Enterprise organisation an administrator must add mash to `allowedChannelPlugins`. Without a channel, mail arrives at the next prompt or tool call. The setup skill writes one command per agent with the right flags ([wake an idle session](https://github.com/bogworks/mash/blob/v0.5.8/docs/install.md#3-optional-wake-an-idle-session)).
- [#875](https://github.com/bogworks/mash/issues/875): `mash doctor` has no idle-wake (channel) or plugin check.
- [#993](https://github.com/bogworks/mash/issues/993): on a host without Claude Code hooks, `doctor`'s delivery row warns for as long as it runs.
- [#1008](https://github.com/bogworks/mash/issues/1008): a first `mash join` interrupted partway leaves a folder that neither a retry nor `--replace` finishes.
- [#1013](https://github.com/bogworks/mash/issues/1013): a join file of another account on the same servers can join a folder that already holds an endpoint.
- [#1097](https://github.com/bogworks/mash/issues/1097): `mashctl status` prints nothing and exits 0 when no server is configured. Someone running it before `mashctl init` meets this, and a script or skill that reads silence as "ok" is misled. Workaround: run `mashctl doctor`, whose config row fails: `config     FAIL  no servers in the configuration`, then `1 problem.` and `hint: mashctl init --config <file>`, exit 1.
- [#1062](https://github.com/bogworks/mash/issues/1062): `mash join` adds a certificate authority to a folder that has servers but no endpoint.
- [#1066](https://github.com/bogworks/mash/issues/1066): `mash join`'s rollback can remove a replaced creds file.

Signing keys, new in 0.5.7:

- [#1246](https://github.com/bogworks/mash/issues/1246): if both `signing.nk` and `signing.pub` are lost from the key store, `mashctl` has no record that a signing key was configured and signs endpoint users with the identity key again, which a strict server refuses. Losing `signing.nk` alone makes `mashctl` refuse instead. Workaround, not yet run: run `mashctl init --config FILE` again with `signing_key` set; until then `mash doctor` shows the sign-in failure.

Setup, found after 0.5.6:

- [#1241](https://github.com/bogworks/mash/issues/1241): the setup skill needs `unzip` or `python3` to unpack the `nats` download, and a clean Debian 13 has neither. Workaround, run on a clean Debian 13 without sudo: the skill took the `nats` `.deb` release asset, checked it against `SHA256SUMS` and unpacked it with `dpkg-deb -x`. With sudo, install `unzip` first.
- [#1242](https://github.com/bogworks/mash/issues/1242): `mash join` with a JWT whose name differs from the address says only "not a join file this mash can read". No workaround has been run; make the join file's JWT name the address.

Found in 0.5.8:

- [#1338](https://github.com/bogworks/mash/issues/1338): `mash inbox` counts the oldest 1000 waiting messages (or 32 MiB); past that the counts are approximate and the output does not yet say so.
- [#1130](https://github.com/bogworks/mash/issues/1130): `mash status` does not warn when Claude Code is older than 2.1.312, although an earlier release note said it does. Nothing in mash warns about it. Workaround: run `claude --version` and compare it with 2.1.312 yourself.
- [#1302](https://github.com/bogworks/mash/issues/1302): `mash doctor`'s refused-mail count can still be one low if `mash serve` is killed while it trims a list of more than 8192 refused messages. Only the count shown is off; nothing is lost.
- [#1301](https://github.com/bogworks/mash/issues/1301): a local server set up before 0.5.8 keeps 64 streams and 128 consumers, and there are no tested steps yet for raising them.

Found in 0.5.7:

- [#1255](https://github.com/bogworks/mash/issues/1255): `mashctl init` does not warn when the NATS operator looks strict and no `signing_key` is set; the new credentials are refused later with "Authorization Violation".
- [#1201](https://github.com/bogworks/mash/issues/1201): the setup skill's `nats` download blocks fail their checksum step in zsh, the default shell on macOS.
- [#1194](https://github.com/bogworks/mash/issues/1194): the setup skill creates `~/.local` even when you chose another install folder.
- [#1179](https://github.com/bogworks/mash/issues/1179): the `send` tool says `question` and `task` mail wakes an idle recipient, but a session started without a channel is not woken; its mail arrives at the next prompt or tool call.

Endpoints and credentials:

- [#879](https://github.com/bogworks/mash/issues/879): the join file can carry a seed in clear text, with no expiry or single use.
- [#867](https://github.com/bogworks/mash/issues/867): `MASH_DANGEROUSLY_SKIP_NATS_ENCRYPTION` is honoured when inherited, with no fresh choice.
- [#880](https://github.com/bogworks/mash/issues/880): with several servers, revocation must reach every one; there are no failover rules.
- [#912](https://github.com/bogworks/mash/issues/912): `endpoint delete` has no drained-delete guard; mail arriving between a drain and a delete is lost.
- [#872](https://github.com/bogworks/mash/issues/872), [#767](https://github.com/bogworks/mash/issues/767): two machines reissuing one endpoint at once can still interleave. The reissue lock covers one machine only.
- [#1081](https://github.com/bogworks/mash/issues/1081): if `mashctl endpoint delete` fails after the key was cancelled, its error is long, internal and writes the address with underscores; run the same command again, as it says (revoking again is safe).
- [#1055](https://github.com/bogworks/mash/issues/1055): the everyday commands say "no credentials here" for an endpoint deleted on this machine; `mash doctor` says it was deleted.
- [#1056](https://github.com/bogworks/mash/issues/1056): `doctor` and `status` trust a local `<creds>.deleted` file to say an endpoint was deleted (a same-user risk).
- [#1064](https://github.com/bogworks/mash/issues/1064): retiring an endpoint keeps the revoked seed on disk as `.creds.deleted`.
- [#1342](https://github.com/bogworks/mash/issues/1342): the `mashctl init` setup-file secret check misses some seed prefixes, and an error can echo a rejected path value (low).
- [#1343](https://github.com/bogworks/mash/issues/1343): the error for a relative `MASH_*` directory variable echoes its value (low).
- [#869](https://github.com/bogworks/mash/issues/869): standing risk: anything running as the same OS user can do what that user can (accepted for mash).

Found after the gate:

- [#1260](https://github.com/bogworks/mash/issues/1260): `mashctl init` prints the full signing public key on its result line, which runs over 80 columns. It is cosmetic and needs no workaround.

One more thing you may see: after a `mash send` that timed out, the server's log can show a filtered `_MASH.settle.*` line. It is expected and harmless.

Some tests are flaky in CI; they do not affect the product. The open ones are listed under the [`test` label](https://github.com/bogworks/mash/issues?q=is%3Aopen+label%3Atest).


### What is not in this release

Two things are not in this release: a `mash inbox` line that says when no `serve` is running ([#958](https://github.com/bogworks/mash/issues/958)), and a count whose cost does not grow with the mailbox's whole history ([#1070](https://github.com/bogworks/mash/issues/1070)). Nothing else is promised here.
