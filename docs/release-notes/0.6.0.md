### Summary

**mash 0.6.0 reads the sender of every message the way the SAP Go SDK does, and that is strict: ten kinds of sender header that older mash accepted are now refused, on live prompts and on mail already stored. See Upgrading.** If every endpoint on your server runs mash, you will notice little, because mash writes headers the strict reader accepts. Mail that is refused is no longer hidden: `mash inbox` and `mash read` show it as a `refused` row with the reason and never its body, and `mash status --detail`, `mash doctor` and `mashctl endpoint inbox` count it. `mash doctor` also checks every endpoint when you have several and none is chosen, and says which mash the plugin runs. Security policy is planned and is not part of this release.

### Upgrading

**This step is one-way:** a problem found after upgrading is fixed by the next release; you do not go back to 0.5.10.

On each machine with endpoints, then on the administrator's machine, in this order. The full steps, in order, are on the [compatibility page](https://github.com/bogworks/mash/blob/v0.6.0/docs/compatibility.md#upgrading-from-0510-to-060); in short:

1. **Check first:** `mash version`, `mash doctor` and, as administrator, `mashctl doctor`. Good is your current release and each doctor ending with no problem and exit code 0.
2. **Install `mash` and `mashctl` 0.6.0** from the same release, with the README's install steps. Endpoints, keys and mail stay where they are.
3. **Update both plugins,** `mash` and `mash-setup`: at a shell `claude plugin update mash@mash` and `claude plugin update mash-setup@mash`. The 0.6.0 plugin that runs the 0.6.0 program is 0.6.0-pin.1, published shortly after the release. A plugin update before then installs 0.6.0 but still runs 0.5.10, so update once more when 0.6.0-pin.1 is out.
4. **Restart each Claude Code session.** A session that is already open keeps running the version it started with until you restart it.
5. **Check again** as in step 1; `mash version` now names 0.6.0.

Machines at mixed versions send and read each other's mail on one server; a machine left behind keeps working. Mail that a 0.5.10 endpoint sent is read by the 0.6.0 rules when a 0.6.0 endpoint receives it.

**If you send mail from something other than mash:** a message whose `Agent-Sender` header has any of the ten shapes below is now refused even when its signature is valid. Mail written by mash is not affected.

### What changed

#### Changed

- **The ten sender headers that are now refused.** The header is refused when it is over 2,048 bytes; when its `ts` is not in UTC (`Z`); when its `name` has a control character, is over 64 characters, or has a broken character escape; when a field appears twice; when its `sub` has a space; when its `sig` is not 64 bytes of base64url text; when it is empty; or when a message carries two. Older mash read these as `verified`, `forged` or `absent`, or took the first or last value. A header with no `Agent-Sender` at all is still `absent`. A few more inputs now read as malformed too: invalid UTF-8, an empty or control-character `sub`, and an unsigned claim with a bad `ts` or `nonce`. A number written `1.0` or `1e0` for `v` now verifies.
- **A live prompt with a malformed sender header is refused with status 400**, `malformed Agent-Sender header`. Two of the ten shapes used to get 401; they now get 400. A prompt that is replayed by a sender who is not in the directory now gets 403 both times; the replay used to get 401. A sender that sends too many prompts too fast is refused with status 401 and the reason `too many recent prompts: try again shortly`; it used to be told a signed header was required, although it had signed. `mash prompt` now starts every error line with `error:` where it used to start some with `mash:`, for example `error: prompt refused: 400 malformed Agent-Sender header`; a script that matches `^mash: ` on its output will miss these lines.
- **`mash doctor` checks every endpoint when you have several.** It used to stop and ask for `--endpoint`. Now it checks each installed endpoint and prints one row for each, with the number of problems and warnings and the first problem, then names the command that shows the first endpoint with a problem. It exits 1 if any endpoint has a problem. `--json` prints each endpoint's report and the totals.
- **The plugin re-checks its downloaded mash once per session, and `mash doctor` says which mash runs.** When a session starts, the plugin confirms its cached copy still matches the release it pins, and replaces a copy that does not (the old file is kept beside it). `mash doctor` shows a `launcher` row: `ok` for the pinned mash, and a warning when the plugin fell back to the mash on your PATH ([#1290](https://github.com/bogworks/mash/issues/1290)).
- **`mash doctor` words the refused-mail row differently.** It reads `no mail was refused` or `4 messages were refused`, with each reason on a line below, and the row is `ok` whatever the count; it used to speak of unverified mail only.
- **`mash prompt` exits 2 for a wrong command line before it reports a configuration problem.**
- **`mashctl init` no longer creates the unused `mash-adoption` bucket.** A server set up earlier keeps that bucket; nothing reads it, and you can delete it; the compatibility page says how.

#### Added

- **Mail that mash refuses is now listed, not hidden.** A message with a faulty header, or one that could not be verified, shows in `mash inbox` and `mash read` as a `refused` row with its reason, and never with its body. `mash status --detail` and `mash doctor` count them, and `mashctl endpoint inbox` adds a `reason` to each refused message. A refused message is not counted as waiting.
- **The first start checks stored mail.** When a session starts, mash reads the mail already stored for the endpoint once, before it delivers, and lists what it refuses. `mash doctor` has rows for that check, and says when the check is still running or was skipped because the state folder cannot be written.
- **`mashctl endpoint inbox --json` shows when each message arrived.** Each message has a `when` field: the time the server stored it, in RFC 3339 and UTC, with a fraction of a second when there is one. The text table is unchanged.

#### Fixed

- **When mash cannot create its state folder, `mash status` no longer says ready and `mash doctor` reports a failed delivery row that names the folder it cannot write.** This is when mail waits for the spool, as the plugin sets it up (`MASH_SPOOL_FROM_START`, or `MASH_SPOOL_REQUIRED`); otherwise mail stays on the channel and is still delivered. Before, the session got no mail while both said all was well.
- **A plain `mash status` run outside a session now sees a state folder mash cannot create.** It checks the folder without writing to it, and says mail cannot be stored when the spool setting (`MASH_SPOOL_FROM_START` or `MASH_SPOOL_REQUIRED`) is set where the shell can see it. See Known issues for when it does not.
- **A restarted endpoint refuses a prompt signed before it started.** The message tells the sender to send the prompt again. See Known issues for the case that is still open.

### Verify your download

Every download has a build attestation; verify it before you run it, with the steps in [Verify what you download](https://github.com/bogworks/mash/blob/v0.6.0/docs/install.md#verify-what-you-download) and [Verify a release](https://github.com/bogworks/mash/blob/v0.6.0/docs/release.md#verify-a-release).

### Known issues

There are 2 known issues. Each has an issue; the issue is the place for detail and any workaround.

- **A prompt signed in the second the endpoint restarted, or sent by a sender whose clock runs ahead, can be replayed for up to about 60 seconds after the restart.** A prompt signed before a restart is refused otherwise. [#1829](https://github.com/bogworks/mash/issues/1829)
- **A plain shell reports a state folder mash cannot create only when the spool setting is visible to it.** `mash status` and `mash doctor` at a shell report it when `MASH_SPOOL_FROM_START` (or its `config.json` key) is set where the shell can see it; a session always reports it. [#1907](https://github.com/bogworks/mash/issues/1907)

### What is not in this release

Security policy, a way to narrow who may mail whom inside an owner, is planned and is not in this release. Nothing else is promised here.
