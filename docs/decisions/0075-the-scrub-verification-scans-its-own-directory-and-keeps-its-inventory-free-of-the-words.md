# The scrub verification scans its own directory and keeps its inventory free of the words

## Context and Problem Statement

ADR 0073 introduced a one-time scrub verification, `go run ./scripts/scrubcheck`, that reads a word list and an
exceptions file from data files beside it. It skipped its own directory, because that directory holds the list itself.
The scrub contract forbids a whole-directory exception (REQ-005, REQ-008), and a skipped directory is one: the words
could return there and no run would see them. Yet the directory must name the words in some places: the list has one per
line, and an exception has to say which occurrence it covers. How does the tool scan its own directory without a
blanket pass, and without the exceptions file becoming a hit that nothing can cover?

## Decision Drivers

* No exception may cover a directory or a whole file; each covers the hits its pattern matches in one file and gives a reason.
* The tool's own files are tracked files like any other and are scanned like any other.
* An exceptions entry names the word it excepts, so the entry itself must not be a hit it cannot excuse.
* The inventory and the tests describe hits and behaviours, so they need not quote the words.
* Still a one-time scrub: no standing guard and nothing in CI.

## Considered Options

* Scan every tracked file, cover the list lines by per-file pattern exceptions, let patterns use `\xHH` escapes, and keep
  the tests and the inventory free of the words (chosen).
* Keep skipping the tool's directory (the decision of ADR 0073).
* Skip only named files in that directory, or list the directory as an exception.
* Keep the words in the exceptions file and add a rule that the tool does not scan that file.

## Decision Outcome

This ADR restates ADR 0073 with the changes below and supersedes it. `scripts/scrubcheck/` holds:

* `words.txt`: the scrub list, one word per line (plurals are generated by the command). The words "operator" and "fleet"
  are not on it. Its header comment holds no listed word. Its seven word lines are hits; each has its own exception
  with the reason "the list itself".
* `exceptions.tsv`: tab-separated entries, each a literal file path, a literal pattern whose
  occurrence on that line contains the excepted word, and a one-line reason. An entry covers every hit its pattern matches in that file, so a list line needs one entry and the list refuses duplicate words. A whole-file entry, a directory or a glob is
  refused, and so is an entry whose path is the exceptions file itself: it is reported and not applied. A pattern may use `\xHH` escapes (two hex digits, either case), decoded before matching; a backslash not
  followed by `x` and two hex digits is literal. An entry that names a listed word writes the first letter of the word
  as an escape, so the line holds no whole word and the file is no hit. An entry that matches nothing is reported, an
  escaped one too.
* `main.go`: `go run ./scripts/scrubcheck` matches case-insensitively and by whole word, over every tracked file,
  the tool's own directory included, and every `-archive` given (tar.gz, tar, zip, or a bare binary, scanned as its
  printable strings). It prints `file:line:word` per hit and reports an exception with no reason and an exception that
  matches nothing.
* `main_test.go`: the unit tests. They build their fixtures from a neutral word list written to a temporary file, so the
  test file holds no listed word. The checked-in list is pinned by the SHA-256 of its normalised content (trimmed
  non-comment lines, lower-cased, joined by newlines), which proves the ruled list without quoting it.
* `inventory.md`: the audit inventory, one row per hit: `file:line:Wn` and a verdict, where Wn is the 1-based position
  of the word in `words.txt` (a plural counts as its base word). It quotes neither the words nor the lines.

The unit tests run under `go test ./...`. Only the scan of the repository does not: nothing runs it automatically, it is
not in CI and not in a test. After the scrub, keeping the words out is left to review, not to a rule. No standing guard
is added.

### Consequences

* Good, because no part of the repository is outside the scan, so the scrub has no blanket pass to hide behind.
* Good, because the exceptions file, the tests and the inventory are plain files a stranger can read, and none of them
  needs an exception of its own beyond the list lines.
* Good, because every exception carries a reason and a stale one is reported.
* Good, because no gate outlives the scrub, as the maintainer asked.
* Bad, because a pattern with an escape is harder to read than the word; the reason column says what it covers.
* Bad, because a change to the list changes the pinned hash, so the test needs the new hash with it.
* Bad, because nothing stops a listed word returning after the scrub except review.

### Confirmation

`scripts/scrubcheck/main_test.go` tests whole-word matching, plurals, case and boundaries, exceptions applied, an
unmatched exception, a missing reason, rejected whole-file entries, binary and archive scanning, symlinks, the scan of
the tool's own directory, the decoding of escapes (valid, uppercase, short and invalid ones taken literally), an escaped
entry that covers its intended hit, an escaped entry that matches nothing and is reported, the hash of the checked-in
list, and that the checked-in exceptions parse clean. `go test ./scripts/scrubcheck/` runs them. A run of
`go run ./scripts/scrubcheck` reports no hit under `scripts/scrubcheck/`.

## Pros and Cons of the Options

### Scan every tracked file with pattern exceptions and escapes (chosen)

* Good, because it satisfies the contract and leaves no unscanned directory.
* Bad, because the list lines need seven exceptions and the patterns need an escape.

### Keep skipping the tool's directory

* Good, because it needs no exception.
* Bad, because it is a whole-directory exception in all but name, which the contract forbids.

### Skip named files, or list the directory as an exception

* Good, because it is short.
* Bad, because it is a whole-file or whole-directory exception again, and a file that is skipped cannot be checked.

### Keep the words in the exceptions file and do not scan it

* Good, because the entries stay readable.
* Bad, because it leaves one file out of the scan, and the rule that leaves it out is the exception the contract forbids.
