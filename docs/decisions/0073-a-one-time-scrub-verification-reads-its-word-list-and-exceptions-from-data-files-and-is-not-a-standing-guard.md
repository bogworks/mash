# A one-time scrub verification reads its word list and exceptions from data files and is not a standing guard

## Context and Problem Statement

mash was built beside a multi-agent deployment and still carries some of that deployment's vocabulary in code, comments,
help text, documentation and release tooling. The maintainer ruled that this is removed in one scrub, checked once
against a word list kept in the repository, and that no standing rule polices the words afterwards. Where do the list,
its exceptions and the check live, and does anything keep running after the scrub?

## Decision Drivers

* The list and the exceptions are data a reviewer can read and change, not constants buried in code.
* An exception must name one occurrence and say why, so it cannot grow into a blanket pass.
* The check must cover source, documentation, the plugin package and the release archives.
* No new permanent gate: the maintainer asked for a one-time scrub, not a standing check.

## Considered Options

* A command under `scripts/scrubcheck` with data files beside it, run by hand (chosen).
* A test under `go test ./...` or a CI job that fails on a listed word.
* A grep one-liner in the release document.

## Decision Outcome

`scripts/scrubcheck/` holds all of it:

* `words.txt`: the scrub list, one word per line (plurals are generated by the command). The words "operator" and "fleet"
  are not on it.
* `exceptions.tsv`: one tab-separated entry per excepted occurrence: a literal file path, a literal pattern whose
  occurrence on that line contains the excepted word, and a one-line reason. A whole-file entry, a directory or a glob is refused.
* `main.go`: `go run ./scripts/scrubcheck` matches case-insensitively and by whole word, over every tracked file and
  every `-archive` given (tar.gz, tar, zip, or a bare binary, scanned as its printable strings). It prints
  `file:line:word` per hit and reports an exception with no reason and an exception that matches nothing.
* `inventory.md`: the audit inventory, one row per hit with a verdict.

The command skips its own directory, because that directory holds the list itself. Nothing runs it automatically: it is
not in CI and not in `go test`. After the scrub, keeping the words out is left to review, not to a rule.

### Consequences

* Good, because the list, the exceptions and the inventory are plain files a stranger can read.
* Good, because every exception carries a reason and a stale one is reported.
* Good, because no gate outlives the scrub, as the maintainer asked.
* Bad, because nothing stops a listed word returning after the scrub except review.
* Bad, because the command trusts the archives it is handed: the person running it builds them.

### Confirmation

`scripts/scrubcheck/main_test.go` tests whole-word matching, exceptions applied, an unmatched exception, a missing reason,
rejected whole-file entries, binary and archive scanning, and that the checked-in list is exactly the ruled one and the
checked-in exceptions parse clean. `go test ./scripts/scrubcheck/` runs them.

## Pros and Cons of the Options

### A command under `scripts/scrubcheck` with data files, run by hand (chosen)

* Good, because it is one-time by construction and reads data, not code.
* Bad, because it needs a person to run it.

### A test or CI job that fails on a listed word

* Good, because it cannot be forgotten.
* Bad, because it is the standing guard the maintainer ruled out, and it would fail on any new prose that needs the word.

### A grep one-liner

* Good, because there is nothing to maintain.
* Bad, because it has no whole-word rule, no exceptions with reasons and no archive scan.
