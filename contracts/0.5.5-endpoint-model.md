## 1. Intent

### Problem

mash has two address forms. Endpoints made by `mashctl add` carry the fixed token `cc` in the first subject slot, have no
group level, and get credentials minted on the mashctl host, so a remote endpoint's private key is copied by hand. The
maintainer has ruled that there are no legacy endpoints, that the address is owner, then group, then instance, and that
every endpoint names its group.

### Desired outcome

In mash 0.5.5 every endpoint has exactly one address form, `<owner>.<group>.<instance>`. It is made by
`mashctl endpoint create`, in a canonical form and a shortcut. Its private key can be made on the endpoint's own machine
so that nothing secret travels. Existing endpoints are moved in one sitting, with a clean rollback until the operator
deletes the old ones. After that, no code that knows the old form remains, except the move command itself, which goes in
0.6.0.

### Motivation

The policy release builds on this address model (standing order 15). Every release that ships the old form adds to
what has to be moved later.

### Success measures

- AT-001 to AT-008 pass live, with transcripts.
- A search of the source for the old form (`cc` slot, `agent_token`, `MASH_AGENT_TOKEN`, `mashctl add`) finds it only
  in the move command, its legacy-record reporting, and test fixtures.
- The maintainer's own endpoints are moved with the shipped commands and the documented steps.

### Non-goals

- Policy of any kind: list sets, narrowing grants, the `policy` verb (the release after).
- Moving endpoints one at a time over days. There is no bridge between old and new addresses.
- High availability, replicas, write quorums (standing order 14).
- More than one NATS server, TLS, or several mashctl hosts: these are not tested and the release notes say so.
- Renaming the other mashctl commands (`init`, `list`, `audit`, `adopt`, `issued`, `inbox`, `limits`, `suspend`,
  `label`) under nouns.
- Mail that waits in an idle mailbox (decision 249): the next contract.

## 2. Actors and journeys

### Actors

- ACT-001: a solo developer on one machine, with nothing above mash installed. Goal: two Claude Code sessions that mail
  each other. Authority: owns the machine, the local NATS server and the account keys. Context: `mashctl init --local`.
- ACT-002: the operator of an existing 0.5.0 deployment whose endpoints are all old-form (today, the maintainer alone).
  Goal: upgrade without losing mail and with a way back.
- ACT-003: an agent driving `mashctl` through `--json` and exit codes.
- ACT-004: an endpoint that runs on a machine other than the mashctl host.

### Primary journeys

- JRN-001 (ACT-001): install mash and mashctl as the README says; `mashctl init --local --owner alice --start`;
  `mashctl endpoint create alice/dev/design` and `mashctl endpoint create alice/dev/review`; install the plugin; start
  two sessions with `MASH_GROUP=dev` and `MASH_NAME=design` or `review`; mail each way; stop the server.
- JRN-002 (ACT-004): on the endpoint's machine `mash credential key --out design.seed` prints the public half; that
  public half reaches the mashctl host as a file; `mashctl endpoint create alice/dev/design --public-key design.pub`
  writes `alice.dev.design.jwt`; the JWT file goes back; `mash credential install` makes the creds file; the session
  connects.
- JRN-003 (ACT-002): the sitting. (1) `mashctl endpoint migrate --all --group dev --dry-run` previews. (2)
  `mashctl endpoint migrate --all --group dev --yes` makes the new endpoints beside the old ones. (3) The operator stops
  every session, upgrades to 0.5.5, and starts each on its new creds. (4) The operator checks every endpoint is
  connected on its new address and mail goes both ways, for as long as they like. (5)
  `mashctl endpoint migrate --all --finish --yes` deletes the old ones.

### Exceptional journeys

- JRN-004: rollback at any time before step 5 of JRN-003 (REQ-013).
- JRN-005: at step 5 an endpoint has not connected on its new address; finish refuses and names it.
- JRN-006: an old name is longer than 32 characters; the dry run marks it refused until `--name` gives the instance.
- JRN-007: a key is revoked; the session using it is dropped and cannot reconnect.
- JRN-008: a group is missing on any command or at session start; a readable refusal names what to add.
- JRN-009: someone types `mashctl add`, `mashctl reissue` or `mashctl retire`; exit 2 names the replacement.
- JRN-010: a move run is killed half way; running it again finishes it and leaves one new identity per endpoint.

## 3. Behavioral requirements

### REQ-001: one address form

- Source: Confirmed (standing orders 10, 15)
- Trigger or precondition: any endpoint is created, addressed or connected.
- MUST: the address is three tokens, owner, group, instance, each matching `[a-z][a-z0-9-]*`, 1 to 32 characters, no
  `--`, no trailing dash; the dotted address is at most 64 characters. Subjects are `agents.<verb>.<owner>.<group>.<instance>`.
  The name rule file is read per token with keys `owner`, `group`, `instance`; the old keys are refused with a message
  naming the new ones.
- Observable postcondition: every subject an endpoint publishes or subscribes to has the owner in slot 1.
- Failure behavior: a token that breaks the rule is refused `name_invalid` or `name_rule`, exit 1, and nothing is written.
- Acceptance: AT-001, AT-005

### REQ-002: every endpoint names its group

- Source: Confirmed (maintainer, 2026-11-17: "No name, no herd", in mash's words: no group, no endpoint)
- Trigger or precondition: `endpoint create`, `endpoint migrate`, or a session start without a group.
- MUST: there is no default group. A command without a group is refused with code `group_missing`, exit 2, and a message
  naming both ways to give one (`--group dev`, `alice/dev/design`). A session started without `MASH_GROUP` (or the
  matching config key) stops at once with a message naming `MASH_GROUP`.
- Observable postcondition: no record, subject, stream or file is created with an implied group.
- Failure behavior: as above; nothing is written.
- Acceptance: AT-005

### REQ-003: `mashctl endpoint create`

- Source: Confirmed for the two forms (standing order 15); Derived for the rest (#729 section 2)
- Trigger or precondition: the account key is present on the mashctl host.
- MUST: `--owner O --group G --name N` and the shortcut `O/G/N` mean the same; a single token is the instance and needs
  `--group`; the owner defaults to the configured owner; a two-token shortcut is refused as ambiguous (exit 2); a form
  that mixes flags and shortcut is refused unless they agree. Output to stdout: text by default, or one JSON document
  (`schema` `mashctl-endpoint@1`, fields `owner`, `group`, `instance`, `address`, `key`, `outcome`, `creds`,
  `next_steps`, `refusal`) with `--json`. `--dry-run` writes nothing. A failure at any step undoes earlier steps.
- Observable postcondition: a directory record, an inbox stream and consumer, an issue record and either a creds file
  (REQ-004 without a public key) or a JWT file (with one).
- Failure behavior: refusal codes `name_invalid`, `name_rule`, `group_missing`, `address_taken`, `key_retired`,
  `creds_exists`, `no_account_key`, exit 1; a server failure is `error`, exit 6.
- Acceptance: AT-001, AT-005, AT-007

### REQ-004: the endpoint can make its own key

- Source: Confirmed (maintainer, 2026-11-17: "Made locally makes sense to me"); the single-machine form without a public
  key is Proposed (DEC-002)
- Trigger or precondition: an endpoint runs on a machine other than the mashctl host, or the operator chooses this path.
- MUST: `mash credential key --out FILE` makes a user key pair on the endpoint's machine, writes the seed to FILE with
  mode 0600, refuses to overwrite, and prints only the public key. `mashctl endpoint create ADDRESS --public-key FILE`
  signs user claims for that public key with the account signing key, records the issue (public key, address, owner,
  issued time; no seed, no JWT), and writes the JWT to a file. `mash credential install --seed FILE --jwt FILE --out CREDS`
  assembles the creds file on the endpoint's machine. `key` and `install` need no NATS connection and no account keys.
- Observable postcondition: the mashctl host holds no seed for that endpoint; the endpoint connects with the assembled
  creds file.
- Failure behavior: a malformed public key, or a public key already issued at another address, is refused, exit 1.
- Acceptance: AT-002

### REQ-005: what a credential may reach

- Source: Confirmed (standing order 12, wide open); Derived for the exact set (#728 section 1.4)
- Trigger or precondition: any credential is signed.
- MUST: for endpoint `O.G.I` with flat key `F`, publish is allowed on `agents.mail.O.*.*`, `agents.prompt.O.*.*`,
  `agents.status.O.*.*`, its own `agents.hb.O.G.I`, and the fixed lines it has in 0.5.0 (reply inboxes, service
  discovery, its own stream and consumer, the directory read, its own lease key); subscribe is allowed on `_INBOX.F.>`,
  its own `agents.prompt.O.G.I` and `agents.status.O.G.I`, service discovery, and `agents.hb.O.*.*`. The owner is a
  literal token in every peer line. A grant with a wildcard in the owner slot is refused.
- Observable postcondition: `mash admin permissions O.G.I` prints exactly this set.
- Failure behavior: n/a (signing refuses an invalid grant).
- Acceptance: AT-001, AT-007

### REQ-006: SAP metadata and the stated departure

- Source: Confirmed (standing orders 5, 10)
- MUST: the service metadata keeps `agent` as the real harness (`claude-code`) and adds `owner`, `group`, `instance`. The
  README's SAP section and `docs/sap.md` state that mash departs from SAP's SHOULD for slot 1 and that discovery by a
  wildcard on the harness slot finds no mash endpoint, while discovery by service name does. No SAP protocol change and
  no SDK divergence.
- Acceptance: AT-001 (metadata read), inspection of the docs

### REQ-007: what is keyed by the address

- Source: Derived (#728 section 1.3)
- MUST: the directory record, inbox stream (`inbox-<flat>`), lease, issue record and retired-key ledger are keyed by the
  flat key `<owner>_<group>_<instance>`; the creds file is `<owner>.<group>.<instance>.creds`. Every deleted endpoint's
  flat key is burned.
- Acceptance: AT-001, AT-003

### REQ-008: how a session names its endpoint

- Source: Derived (#729 section 8)
- MUST: a session reads `MASH_OWNER` (or the configured owner), `MASH_GROUP` and `MASH_NAME`; the three make the address.
- Failure behavior: a missing group is REQ-002; a missing name keeps 0.5.0's behaviour.
- Acceptance: AT-001, AT-005

### REQ-009: reissue, delete, list, show

- Source: Derived (#729 section 4)
- MUST: `mashctl endpoint reissue ADDRESS` (and `--all --yes`, `--changed --yes`) gives an endpoint a fresh credential
  and revokes the old; `mashctl endpoint delete ADDRESS` revokes the key, removes the record and inbox, and renames the
  creds file `.retired-<time>` (or removes it with `--delete-creds`); `list` and `show` change nothing. Each takes
  `--json`; the changing ones take `--dry-run`. Exit codes follow ADR 0144.
- Acceptance: AT-001, AT-007

### REQ-010: the old form is gone

- Source: Confirmed (standing orders 11, 15)
- MUST: `mashctl add`, `mashctl reissue`, `mashctl retire`, the `cc` address form, `agent_token` and `MASH_AGENT_TOKEN`
  are removed. The three old commands run nothing, exit 2 and name their replacement. No aliases.
- Acceptance: AT-005, the source search in section 1

### REQ-011: the move (subject to DEC-001)

- Source: Confirmed for one sitting (maintainer, 2026-11-17, choice A); Derived for the command (#728, #729)
- Trigger or precondition: old-form endpoints exist; the operator runs the 0.5.5 mashctl.
- MUST: `mashctl endpoint migrate --all --group G --dry-run` lists every old endpoint with its new address and outcome
  (`planned` or `refused` with a reason) and changes nothing. `--yes` makes, for each, the new record, inbox and
  credential (from the endpoint's public key under REQ-004, the flag spelled by the herd), copies the unread mail from
  the old inbox into the new one, and leaves the old record, inbox and credential untouched. `--name N` sets the
  instance for one endpoint whose old name does not fit. A bare `migrate` exits 2. A run again on a moved endpoint
  reports `unchanged`. Output and JSON as #729 section 3.1.
- Observable postcondition: each old endpoint has a new identity; its old session still works.
- Failure behavior: a refusal on one endpoint does not stop the others; the run's outcome is `partial`, exit 5.
- Acceptance: AT-003, AT-005, AT-006

### REQ-012: finishing the move

- Source: Confirmed (choice A: "finish waits until the operator says the fleet is healthy", in the planner's relay)
- MUST: `mashctl endpoint migrate --all --finish --yes` refuses, naming each endpoint, while any moved endpoint has not
  connected on its new address, unless `--force`. Otherwise it revokes the old credentials, deletes the old records and
  inboxes, and reports what it removed. Its output, its `--help` and `docs/operations.md` say it cannot be undone.
- Acceptance: AT-003, AT-005

### REQ-013: rollback before finish

- Source: Confirmed (maintainer, 2026-11-17: "only if we have a clean rollback in case it blows up")
- Trigger or precondition: the move has been applied, and finish has not run.
- MUST: with the 0.5.0 `mash` binary and the old creds files, every old endpoint connects on its old address and reads
  all its mail, including mail that arrived during the switch. Mail that reached a new inbox can be read with
  `mash inbox` under the new creds. `mashctl endpoint migrate --rollback --all` removes the new identities (record,
  inbox, credential revoked, issue record marked) without burning their flat keys, so the sitting can run again; it
  refuses while a new inbox holds unread mail, unless `--force`. It leaves the old endpoints as they were and refuses
  after finish. `docs/operations.md` gives these as numbered operator steps.
- Observable postcondition: after rollback the deployment behaves as 0.5.0 did.
- Acceptance: AT-004

### REQ-014: what a revoked session sees

- Source: Derived (core, 2026-11-17)
- MUST: revoking a key (by `endpoint delete`, `endpoint reissue`, `migrate --finish` or `credential revoke`) updates the
  account JWT on every server mashctl knows; the server closes that key's live connections and refuses reconnects as not
  authorized; `mash status` reports the authorization failure.
- Acceptance: AT-001, AT-003

### REQ-015: old records do not break new commands

- Source: Derived (core, 2026-11-17)
- MUST: while old records exist, every 0.5.5 command that reads the directory reports an old record as legacy and never
  aborts because of one. `audit` lists old endpoints, moved endpoints, and old inboxes not yet empty.
- Acceptance: AT-008

### REQ-016: documentation

- Source: Derived
- MUST: the README quick start follows JRN-001 and names a group; the README states the SAP departure; `docs/mashctl.md`
  covers the `endpoint` commands; `docs/operations.md` covers JRN-003 and JRN-004; the release notes say what is not
  tested (non-goals) and lead with the breaking change.
- Acceptance: inspection; the maintainer follows the README (validation)

### REQ-017: the command-line standard

- Source: Confirmed (standing order 13); Proposed for the two verbs (DEC-003)
- MUST: the `endpoint` commands conform to the CLI standard 1.0.1 (noun, verb, at most one positional, `--json` on
  reads, `--dry-run` on changes, readable refusals). `reissue` is added to the standard's verb table; `migrate` is a
  recorded exception in ADR 0145 that ends when it is removed.
- Acceptance: the command-tree test for the `endpoint` noun (AT-007)

## 4. System boundaries

### BND-001: mash and anything above it

- Charter or seam page: none exists (finding F-1); standing orders 1, 2, 6, 8 apply.
- Owned responsibility: endpoints, their addresses, credentials, mailboxes, and the move.
- Allowed interactions: anyone may run `mashctl` and `mash` and read their JSON.
- Prohibited interactions and effects: no requirement, flag, subject, key, field, error text or test names a layer
  above mash.
- Enforcement: the forbidden-word test that exists today, extended to the new code.
- Approval to change: the maintainer.

### BND-002: SAP

- Charter or seam page: none; standing order 5.
- Owned responsibility: what mash puts in the three slots.
- Prohibited: any change to the SAP protocol or divergence from the SAP Go SDK.
- Enforcement: the SDK compatibility gate that exists today.
- Approval to change: none possible (standing order 5).

### BND-003: the NATS server

- Owned responsibility: mash uses account JWTs, user JWTs and the account revocation list as in 0.5.0.
- Prohibited: changes to server configuration beyond what `init --local` writes today.
- Enforcement: prose.

### What this component must not know

- Standing orders checked: `standing-orders/mash.md` as of 2026-11-17. Conflicts: none (order 15 replaces order 10's last
  sentence, as order 15 says).
- Concepts of layers above that appear nowhere in a requirement, flag, subject, key, field, error text or test: range,
  herd, lane, wrangler, homerange, rangehand, lane roles, labels and rule languages of any layer above it, trailboss,
  any herd's name.

### Existing behavior to preserve

- Mail delivery, sender signing and the trust labels, hook and channel delivery, the plugin's tools.
- `mashctl init --local` and its flags; the commands not named in REQ-009 and REQ-010 keep their 0.5.0 spellings.
- The several-servers flags (`--servers`, `--sys-creds`) on every command that writes.

## 5. Invariants and constraints

### INV-001: no secret leaves where it belongs

No seed or creds file contents are printed, logged, mailed or stored by mashctl in the REQ-004 path; no command prints a
seed or a JWT to stdout except `endpoint create --public-key` without `--out`, which prints the JWT (not secret).

### INV-002: no reach across owners

No credential signed by 0.5.5 can publish or subscribe on another owner's subjects.

### INV-003: nothing old changes before finish

From `migrate --yes` until `migrate --finish`, the old records, inboxes, consumers and credentials are byte-for-byte as
they were, except for mail added to the old inboxes by senders.

### INV-004: no mail lost by the move

Mail in an old inbox when `migrate --yes` runs is in the new inbox afterwards and stays in the old inbox until finish.

### Security, reliability, compatibility, performance

- NFR-001: a killed run of any changing `endpoint` command leaves either nothing or a state that the same command, run
  again, completes.
- NFR-002: tested on one NATS server made by `init --local`; the release notes say multi-server and TLS are not tested.
- NFR-003: build size, core: 14 person-days (12.5 for the model, the move and its rollback, plus 1.5 for REQ-004);
  ctl: 12 person-days (endpoint noun 3, migrate 3, credential key and install 1, removals 1, goldens and command-tree
  test 2, docs 2), after core's model lands. About 26 person-days in all.

## 6. Acceptance contract

All runs: one machine, one local NATS server from `mashctl init --local`, scratch homes, no tool above mash installed.

### AT-001: the solo developer, standalone

Given a fresh scratch home, when the README quick start is followed (`init --local --owner alice`, `endpoint create
alice/dev/design`, `endpoint create alice/dev/review`, plugin, two sessions with `MASH_GROUP=dev`), then mail goes each
way verified, `endpoint list --json` shows both with `group` `dev`, the service metadata shows `agent` `claude-code`
and the three parts, `mash admin permissions alice.dev.design` prints REQ-005's set, and after `endpoint delete
alice/dev/review` the review session's connection is closed, a reconnect is refused, and `mash status` says why.

### AT-002: the endpoint makes its key

Given two scratch homes A (mashctl host) and B (endpoint), when B runs `mash credential key`, A runs `endpoint create
alice/dev/design --public-key`, and B runs `mash credential install` and connects, then the endpoint mails a peer, and
a search of all captured output and of A's home for the seed finds nothing.

### AT-003: the sitting

Given two old-form endpoints `design` and `review` made and run by the 0.5.0 binaries, with three unread messages in
design's inbox, when `migrate --all --group dev --dry-run`, then `--yes`, then the switch to 0.5.5, then
`--finish --yes` are run, then: after the dry run nothing changed; after `--yes` both old sessions still mail each other
and the new records, inboxes and credentials exist; after the switch design reads the three messages once each and the
two new endpoints mail each other; after finish a connect with an old creds file is refused, the old records and inboxes
are gone, and `audit` is clean.

### AT-004: rollback, then the sitting again

Given AT-003 up to the switch, plus one message sent to each new address, when the operator follows the rollback steps
of `docs/operations.md`, then both old endpoints connect with the 0.5.0 binary and old creds, every old message is
present, the message in each new inbox was readable with `mash inbox` under the new creds, `migrate --rollback --all`
refused while that mail was unread and succeeded after, and the new endpoints are gone. The 0.5.0 `mashctl list`,
`retire` and `audit` work with no 0.5.5 record left behind. Then AT-003 runs again from `--yes` to finish and passes,
reusing the same addresses.

### AT-005: refusals

Each of these is refused with the stated exit code and a message that names what to type: `endpoint create design` with
no group (2); `endpoint create alice/design` (2); a session with no `MASH_GROUP`; `migrate` with no endpoint and no
`--all` (2); a 40-character old name until `--name` is given (refused, exit 5 for the run); `migrate --finish` while one
moved endpoint has not connected (1); `migrate --yes` again on a moved endpoint (`unchanged`, 0); `mashctl add`,
`mashctl reissue`, `mashctl retire` (2).

### AT-006: a killed move

Given AT-003's start, when `migrate --all --group dev --yes` is killed after the first endpoint's credential is made and
before its record is written, and run again, then each endpoint has exactly one new identity.

### AT-007: the command contract

Golden text and JSON for `endpoint create` (planned, created, each refusal), `migrate` (plan, apply, finish, partial),
`delete`, `reissue` and the removed-command messages. `--dry-run` leaves the directory, the issue record and the config
directory byte-identical. The command-tree test walks the `endpoint` noun (at most one positional, `--json` valid,
`--dry-run` changes nothing, a bad flag exits 2, `--help` has an example).

### AT-008: old records present

Given old-form records in the directory, every 0.5.5 command that reads the directory (`endpoint list`, `endpoint show`,
`audit`, `who`, the directory watch) completes and reports them as legacy.

## 7. Assumptions and open decisions

### Confirmed assumptions

- The maintainer is the only user with old-form endpoints (maintainer, 2026-11-16).
- His deployment runs on one NATS server and one mashctl host.
- The 0.5.0 binaries can be kept until finish.

### Unresolved decisions

- DEC-001 [BLOCKING]: keep `mashctl endpoint migrate` (recommended), or drop it for an operator procedure of
  `endpoint create` plus the 0.5.0 `mashctl retire`. Dropping saves 0 to 0.5 days and loses the preview, the mail copy and
  the connected check (core's costing, 2026-11-17). If dropped, REQ-011 and REQ-012 become a tested procedure in
  `docs/operations.md`, REQ-015 stays, and AT-003 to AT-006 run against the procedure. Owner: the maintainer.
- DEC-002 [not blocking]: does `endpoint create` without `--public-key` (mashctl makes the key, as `add` did) stay, for
  endpoints on the mashctl host? Recommended: yes, both forms. Owner: the maintainer.
- DEC-003 [not blocking]: `reissue` added to the CLI standard's verb table, `migrate` a recorded exception. Owner: the
  maintainer; the planner edits the standard.

### Delegated to the herd

- Flag spellings within the CLI standard, including how `migrate` takes the endpoints' public halves.
- JSON field order, refusal wording, test layout, ADR amendments listed in #728 section 5.

### Changes that need approval

- Any change to SAP subjects beyond REQ-001, to the permission set in REQ-005, or any new default: the maintainer.
- Any old-form code kept past 0.6.0: the maintainer.
