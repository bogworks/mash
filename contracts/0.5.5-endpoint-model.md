Revision 9 changes (the planner, 2026-11-18, on the final gate's security finding G1): reply inboxes are inside the
owner's wall. An endpoint's reply-inbox prefix is `_INBOX.O.F`; it may publish replies only to `_INBOX.O.>` and
subscribe only to `_INBOX.O.F.>`. Before this, every endpoint could publish to `_INBOX.>`, and a live check showed that
another owner could forge a service-discovery answer (a false "online") and replay a genuine presence answer into an
endpoint's session. AT-003 and AT-005 gain the negative test (REQ-005, INV-002).

Revision 8 changes (the planner, 2026-11-18, text only): AT-005's create case no longer says the command reports
that all three servers took the account update. Create signs a user credential with the account's signing key and
changes no account record, so there is nothing for the servers to acknowledge. The case now checks that the new
endpoint's credential is accepted by each of the three servers. Reissue and delete, which change the account record,
report the servers' acknowledgement.

Revision 7 changes (the planner, 2026-11-17): the clock-skew case leaves AT-005, since it cannot be produced honestly
in containers (mash's Go code reads the clock through the vDSO, and containers share the kernel's clock). Where mash's
own code reads the time to decide something in this contract, an in-process test with an injected clock covers the
skewed case (AT-004). No clock offset exists in a shipped binary. AT-005 runs as a CI job on the self-hosted Linux
runners, advisory until it has passed twice.

Revision 6 changes (the planner, 2026-11-17, within the maintainer's stated options: "testing doesn't happen on dev
boxes unless it's in a container or a VM, isolated, and can be easily thrown away afterwards"): AT-005's nodes are
rootless containers the test builds and destroys, not network namespaces (NFR-002, AT-005); what containers do not
prove is stated once as a known limit.

Revision 5 changes (the maintainer, 2026-11-17, relayed by the operations lead): no test runs on production hosts.
AT-005's three machines are isolated nodes that the test itself creates and destroys on one host: each its own network
namespace inside an unprivileged user namespace, joined by virtual links, with its own home, configuration and processes
(NFR-002, AT-005). No host access, test account or install outside the test. The assumption about hosts that operations
names is withdrawn.

Revision 4 changes (the maintainer's comments of 2026-11-17 on the guide to decision 250): the release is tested
across separate machines, over TLS, on a cluster of NATS servers and from two mashctl machines (NFR-002, AT-005,
ACT-004, JRN-008, DEC-004); "untested multi-server use" leaves the accepted risks; a group that cannot be changed is an
accepted risk owned by the maintainer; DEC-002 closed yes; DEC-004 records how a second mashctl machine signs, and
names it the hardest of the three; NFR-003 re-costed.

Revision 3 changes (the critic's surviving findings): the endpoint-made key is the default path, and mashctl making the
key is an explicit same-host exception (B2); unread mail at the cut is an accepted risk (B4); a group is never stored
or inferred, and cannot be changed later (B5); section 8 asks for the final gate's evidence (B6); one exit code for

planted cross-owner attempt (N6); the session refusal states what is observed (N7).

Revision 2 changes: the maintainer ruled a hard cut. No move command, no rollback verb and no handling of old state in
the product; DEC-001 closed.

## 1. Intent

### Problem

mash has two address forms. Endpoints made by `mashctl add` carry the fixed token `cc` in the first subject slot, have no
group level, and get credentials minted on the mashctl host, so a remote endpoint's private key is copied by hand. The
maintainer has ruled: there are no legacy endpoints; the address is owner, then group, then instance; every endpoint
names its group; the endpoint makes its own key; and 0.5.5 is a hard cut.

### Desired outcome

mash 0.5.5 knows one endpoint model and nothing else. Every endpoint has the address `<owner>.<group>.<instance>` and is
made by `mashctl endpoint create` in a canonical form or a shortcut. Its private key is made on its own machine, so
nothing secret travels. The old form is gone from the code: 0.5.5 does not read, convert or tolerate old records,
addresses or credentials.

### Motivation

The policy release builds on this model (standing order 15). No one uses mash yet, so a hard cut costs nothing that a
soft cut would save (maintainer, 2026-11-17).

### Success measures

- AT-001 to AT-005 pass live, each with a run record (section 8).
- A search of the source, tests and docs for the old form (`cc` slot, `agent_token`, `MASH_AGENT_TOKEN`, `mashctl add`,
  legacy parsers) finds it only in the release notes and in the messages of REQ-009.

### Non-goals

- Moving existing endpoints. That is a one-time operator script outside mash, owned by operations, with its own
  rollback plan (command-line standard rule 23); this contract names that it exists and nothing more (section 7).
- Carrying mail over the cut. Mail still unread in old inboxes when the operator cuts over is not carried into 0.5.5.
  This is an accepted risk, accepted by the maintainer in his hard-cut ruling of 2026-11-17.
- Policy of any kind: list sets, narrowing grants, the `policy` verb (the release after).
- High availability, replicas, write quorums (standing order 14).
- Renaming the other mashctl and mash commands under nouns (the command-line standard's table defers them to mash's
  major revision).
- Mail that waits in an idle mailbox (decision 249): the next contract.

## 2. Actors and journeys

### Actors

- ACT-001: a solo developer on one machine, with nothing above mash installed. Goal: two Claude Code sessions that mail
  each other. Authority: owns the machine, the local NATS server and the account keys. Context: `mashctl init --local`.
- ACT-002: an agent driving `mashctl` and `mash` through `--json` and exit codes.
- ACT-003: an endpoint that runs on a machine other than the mashctl host.
- ACT-004: an operator who runs mashctl from two machines against one deployment of several NATS servers reached over
  TLS.

### Primary journeys

- JRN-001 (ACT-001): install mash and mashctl as the README says; `mashctl init --local --owner alice --start`; for
  each of `design` and `review`: `mash key create --out design.seed` (prints the public key to `design.pub`),
  `mashctl endpoint create alice/dev/design --public-key design.pub` (writes `alice.dev.design.jwt`),
  `mash credential create --seed design.seed --jwt alice.dev.design.jwt` (writes the creds file); install the plugin;
  start two sessions with `MASH_GROUP=dev` and `MASH_NAME=design` or `review`; mail each way; stop the server.
- JRN-002 (ACT-003): as JRN-001 for one endpoint, with `mash key create` and `mash credential create` run on the
  endpoint's machine and `mashctl endpoint create` on the mashctl host; only the public key file and the JWT file
  travel between them.

### Exceptional journeys

- JRN-003: a key is replaced or revoked (`endpoint reissue`, `endpoint delete`); the session using the old key is dropped
  and cannot reconnect.
- JRN-004: a group is missing on any command or at session start; a readable refusal names what to add.
- JRN-005: someone types `mashctl add`, `mashctl reissue` or `mashctl retire`; exit 2 names the replacement.
- JRN-006: a `create`, `reissue` or `delete` run is killed half way; the same command run again completes it.
- JRN-007: an endpoint of one owner tries to reach an endpoint of another owner; the server refuses it.

### Journey across machines

- JRN-008 (ACT-003, ACT-004): on a deployment of three NATS servers on three machines, clustered and reached over TLS,
  the operator creates endpoints from either of two mashctl machines; each endpoint runs on a machine other than the
  mashctl machine that created it and other than the server it connects to; each makes its own key, and only the public
  key file and the JWT file travel.

## 3. Behavioral requirements

### REQ-001: one address form

- Source: Confirmed (standing orders 10, 15)
- Trigger or precondition: any endpoint is created, addressed or connected.
- MUST: the address is three tokens, owner, group, instance, each matching `[a-z][a-z0-9-]*`, 1 to 32 characters, no
  `--`, no trailing dash; the dotted address is at most 64 characters. Subjects are
  `agents.<verb>.<owner>.<group>.<instance>`. The name rule file is read per token with keys `owner`, `group`,
  `instance`.
- Observable postcondition: every subject an endpoint publishes or subscribes to has the owner in slot 1.
- Failure behavior: a token that breaks the rule is refused `name_invalid` or `name_rule`, exit 1, and nothing is written.
- Acceptance: AT-001, AT-003

### REQ-002: every endpoint names its group

- Source: Confirmed (maintainer, 2026-11-17: no group, no endpoint)
- Trigger or precondition: `endpoint create`, or a session start, without a group.
- MUST: there is no default group, and nothing in 0.5.5 stores or infers one: not a config key, not a previous command,
  not the environment beyond `MASH_GROUP` for a session. A command without a group is refused with code `group_missing`,
  exit 2, and a message naming both ways to give one (`--group dev`, `alice/dev/design`). A session started without
  `MASH_GROUP` stops at once, exit 2, with a message naming `MASH_GROUP`. An endpoint's group cannot be changed later:
  moving an endpoint to another group means creating a new endpoint and deleting the old one, whose address is then
  burned (REQ-007). `endpoint create --help` and `docs/mashctl.md` say so.
- Observable postcondition: no record, subject, stream, lease or file is created with an implied group.
- Failure behavior: as above; nothing is written.
- Acceptance: AT-003

### REQ-003: `mashctl endpoint create`

- Source: Confirmed for the two naming forms (standing order 15) and the key path (maintainer, 2026-11-17, ruling B);
  Derived for the rest (#729 section 2)
- Trigger or precondition: the account key is present on the mashctl host.
- MUST: `--owner O --group G --name N` and the shortcut `O/G/N` mean the same; a single token is the instance and needs
  `--group`; the owner defaults to the configured owner; a two-token shortcut is refused as ambiguous (exit 2); a form
  that mixes flags and shortcut is refused unless they agree. The key comes from the endpoint: `--public-key FILE` is
  the default path (REQ-004). The one exception is an explicit flag (proposed `--make-key`, DEC-002) that makes the key
  pair on the mashctl host and writes the creds file there; it is documented as only for an endpoint that runs on the
  mashctl host, and is never the path for an endpoint on another machine. With neither, the command is refused
  `key_missing`, exit 2, naming both. Output to stdout: text by default, or one JSON document (`schema`
  `mashctl-endpoint@1`, fields `owner`, `group`, `instance`, `address`, `key`, `outcome`, `jwt_path` or `creds_path`,
  `next_steps`, `refusal`) with `--json`. `--dry-run` writes nothing. A failure at any step undoes earlier steps.
- Observable postcondition: a directory record, an inbox stream and consumer, an issue record, and a JWT file (or, with
  the same-host flag, a creds file).
- Failure behavior: usage refusals exit 2 (`group_missing`, `key_missing`, a two-token or disagreeing form); refusals of
  the request exit 1 (`name_invalid`, `name_rule`, `address_taken`, `key_retired`, `public_key_invalid`,
  `public_key_issued`, `file_exists`, `no_account_key`); a server failure is `error`, exit 6.
- Acceptance: AT-001, AT-003, AT-004

### REQ-004: the endpoint makes its own key

- Source: Confirmed (maintainer, 2026-11-17: "Made locally makes sense to me")
- Trigger or precondition: any new endpoint, or any replacement of an endpoint's key.
- MUST: `mash key create --out FILE` makes a user key pair on the endpoint's machine, writes the seed to FILE with mode
  0600, refuses to overwrite, and writes the public key to `FILE` with `.seed` replaced by `.pub` (or `--pub-out FILE`).
  `mashctl endpoint create ADDRESS --public-key FILE` signs user claims for that public key with the account signing
  key, records the issue (public key, address, owner, issued time; no seed, no JWT), and writes the JWT to a file
  (`--jwt-out FILE`, default `<owner>.<group>.<instance>.jwt` in the working directory, mode 0600, never over an existing
  file). `mash credential create --seed FILE --jwt FILE [--out CREDS]` assembles the creds file on the endpoint's machine
  (default: the path `mash` reads for that address). `mash key create` and `mash credential create` need no NATS
  connection and no account keys.
- Observable postcondition: the mashctl host holds no seed for that endpoint; the endpoint connects with the assembled
  creds file.
- Failure behavior: a malformed public key (`public_key_invalid`) or a public key already issued at another address
  (`public_key_issued`) is refused, exit 1; a seed and a JWT for different public keys are refused by
  `mash credential create`, exit 1.
- Acceptance: AT-001, AT-002, AT-003

### REQ-005: what a credential may reach

- Source: Confirmed (standing order 12, wide open); Derived for the exact set (#728 section 1.4)
- Trigger or precondition: any credential is signed.
- MUST: for endpoint `O.G.I` with flat key `F`, publish is allowed on `agents.mail.O.*.*`, `agents.prompt.O.*.*`,
  `agents.status.O.*.*`, its own `agents.hb.O.G.I`, replies to its own owner's inboxes `_INBOX.O.>`, and the fixed
  lines it has in 0.5.0 (service discovery, its own stream and consumer, the directory read, its own lease key);
  subscribe is allowed on its own reply inboxes `_INBOX.O.F.>`, its own `agents.prompt.O.G.I` and
  `agents.status.O.G.I`, service discovery, and `agents.hb.O.*.*`. The endpoint's reply-inbox prefix is `_INBOX.O.F`.
  The owner is a literal token in every peer line and in both inbox lines. A grant with a wildcard in the owner slot
  is refused.
- Observable postcondition: `mash admin permissions O.G.I` prints exactly this set.
- Failure behavior: a publish outside the set is refused by the server with a permissions violation.
- Acceptance: AT-001, AT-003, AT-004

### REQ-006: SAP metadata and the stated departure

- Source: Confirmed (standing orders 5, 10)
- MUST: the service metadata keeps `agent` as the real harness (`claude-code`) and adds `owner`, `group`, `instance`. The
  README's SAP section and `docs/sap.md` state that mash departs from SAP's SHOULD for slot 1 and that discovery by a
  wildcard on the harness slot finds no mash endpoint, while discovery by service name does. No SAP protocol change and
  no SDK divergence.
- Acceptance: AT-001 (metadata read); inspection of the docs

### REQ-007: what is keyed by the address

- Source: Derived (#728 section 1.3)
- MUST: the directory record, inbox stream (`inbox-<flat>`), lease, issue record and retired-key ledger are keyed by the
  flat key `<owner>_<group>_<instance>`; the creds file is `<owner>.<group>.<instance>.creds`. Every deleted endpoint's
  flat key is burned, and `endpoint create` refuses a burned address (`key_retired`).
- Acceptance: AT-001, AT-003

### REQ-008: how a session names its endpoint

- Source: Derived (#729 section 8)
- MUST: a session reads `MASH_OWNER` (or the configured owner), `MASH_GROUP` and `MASH_NAME`; the three make the address.
- Failure behavior: a missing group is REQ-002; a missing name keeps 0.5.0's behaviour.
- Acceptance: AT-001, AT-003

### REQ-009: the old form is gone

- Source: Confirmed (standing orders 11, 15; maintainer, 2026-11-17, the hard cut)
- MUST: `mashctl add`, `mashctl reissue`, `mashctl retire`, the `cc` address form, `agent_token`, `MASH_AGENT_TOKEN`, the
  legacy parsers and every code path that reads an old record are removed. The three old commands run nothing, exit 2
  and name their replacement (command-line standard rule 13). No aliases. 0.5.5 does not read, convert or tolerate old
  records, addresses or credentials.
- Acceptance: AT-003; the source search of section 1

### REQ-010: reissue, delete, list, show

- Source: Derived (#729 section 4)
- MUST: `mashctl endpoint reissue ADDRESS --public-key FILE` (or the same-host flag of REQ-003) signs a credential for the
  new public key, writes the JWT file as REQ-004 does, and revokes the old key; the bulk forms `--all --yes` and
  `--changed --yes` take the same-host flag only, since one public key cannot serve many endpoints.
  `mashctl endpoint delete ADDRESS` revokes the key, removes the record and inbox, burns the address, and renames a creds
  file it finds on the mashctl host `.retired-<time>` (or removes it with `--delete-creds`). `list` and `show` change
  nothing. Each takes `--json`; the changing ones take `--dry-run`. Exit codes follow ADR 0144.
- Acceptance: AT-001, AT-004

### REQ-011: what a revoked session sees

- Source: Derived (core, 2026-11-17)
- MUST: revoking a key (by `reissue` or `delete`) updates the account JWT on every server mashctl knows; the server
  closes that key's live connections and refuses reconnects as not authorized; `mash status` reports the authorization
  failure.
- Acceptance: AT-001

### REQ-012: documentation

- Source: Derived
- MUST: the README quick start follows JRN-001 and names a group; the README states the SAP departure; `docs/mashctl.md`
  covers the `endpoint` commands, the key commands, the same-host flag and its limit, and that a group cannot be changed;
  the release notes lead with the hard cut (0.5.5 does not work with endpoints made by 0.5.0, and mail unread in them is
  not carried over: make new ones) and say what is not tested.
- Acceptance: inspection; the maintainer follows the README (validation)

### REQ-013: the command-line standard

- Source: Confirmed (standing order 13; command-line standard 1.1.1)
- MUST: `mashctl endpoint create|reissue|delete|list|show`, `mash key create` and `mash credential create` conform to the
  command-line standard 1.1.1: noun, verb from the table (`create`, `reissue`, `delete`, `list`, `show`), at most one
  positional, `--json` on reads, `--dry-run` on changes, readable refusals, no aliases, nothing for one-time use
  (rule 23). The command-tree test of rule 22 walks these three nouns in full; the commands the standard's table defers
  to mash's major revision are listed in the test as known exceptions, by name, and nothing else is excepted.
- Acceptance: AT-004

## 4. System boundaries

### BND-001: mash and anything above it

- Charter or seam page: none exists (finding F-1); standing orders 1, 2, 6, 8 apply.
- Owned responsibility: endpoints, their addresses, keys, credentials and mailboxes.
- Allowed interactions: anyone may run `mashctl` and `mash` and read their JSON.
- Prohibited interactions and effects: no requirement, flag, subject, key, field, error text or test names a layer
  above mash.
- Enforcement: the forbidden-word test that exists today, extended to the new code.
- Approval to change: the maintainer.

### BND-002: SAP

- Charter or seam page: none; standing order 5.
- Owned responsibility: what mash puts in the three slots.
- Prohibited: any change to the SAP protocol or divergence from the SAP Go SDK.
- Enforcement: the SDK compatibility gate that exists today.
- Approval to change: none possible (standing order 5).

### BND-003: the NATS server

- Owned responsibility: mash uses account JWTs, user JWTs and the account revocation list as in 0.5.0.
- Prohibited: changes to server configuration beyond what `init --local` writes today. The server configuration of
  AT-005 (certificate authority, server certificates, cluster routes) is written by the test harness, not by mash;
  mash writes none of it, and the release notes say how an operator sets it up.
- Enforcement: prose.

### What this component must not know

- Standing orders checked: `standing-orders/mash.md` as of 2026-11-17, with order 15 amended for the hard cut. Conflicts:
  none.
- Concepts of layers above that appear nowhere in a requirement, flag, subject, key, field, error text or test: range,
  herd, lane, wrangler, homerange, rangehand, lane roles, labels and rule languages of any layer above it, trailboss,
  any herd's name.

### Existing behavior to preserve

- Mail delivery, sender signing and the trust labels, hook and channel delivery, the plugin's tools.
- `mashctl init --local` and its flags; the commands not named in REQ-009, REQ-010 and REQ-013 keep their 0.5.0
  spellings.
- The several-servers flags (`--servers`, `--sys-creds`) on every command that writes.

## 5. Invariants and constraints

### INV-001: no secret leaves where it belongs

No command prints a seed or a JWT, or writes a seed anywhere but the endpoint's own machine in the default path. mashctl
never reads, stores or logs a seed in the default path. Files that hold a seed or a JWT are written with mode 0600.

### INV-002: no reach across owners

No credential signed by 0.5.5 can publish or subscribe on another owner's subjects. Reply subjects are inside the
owner's wall: an endpoint's replies go only to `_INBOX.O.>` of its own owner, so an endpoint of another owner cannot
answer, forge or replay a reply into it.

### Security, reliability, compatibility, performance

- NFR-001: a killed run of `endpoint create`, `reissue` or `delete` leaves either nothing or a state that the same
  command, run again, completes.
- NFR-002: tested both on one NATS server made by `init --local` (AT-001 to AT-004) and across separate machines
  (AT-005): three NATS servers on three machines, clustered, with TLS on client and route connections; endpoints on
  machines other than the server they connect to and the mashctl machine that created them; two mashctl machines.
  A machine here is a rootless container that the test creates and destroys (AT-005), never a production host: the
  test creates no account, places nothing on a host and needs no access outside the host it runs on. Known limit,
  stated once: containers share the host's kernel and clock, so AT-005 does not prove behavior across separate kernels,
  and it does not prove behavior under real clock drift between machines. Where the NATS server, not mash, reads the
  time (for example JWT expiry and revocation times as the server applies them), that is the server's and not mash's to
  test.
- NFR-003: build size: core 10.5 person-days for revision 3's scope (address and subjects 2, permissions and keyed
  storage 2.5, removal of the old form 3, REQ-004 1.5, live proof, docs and release notes 1.5), plus 4.5 for AT-005
  (TLS and cluster configuration and certificates 1.5, a harness of test-made containers 1.5, the two-mashctl-machine proof
  1.5) and a reserve of 2 for what the first real run finds: 15 to 17. ctl 8 (endpoint noun 3, key and credential
  commands 1, removals 1, goldens and command-tree test 1.5, docs 1.5), plus 0.5 to 1 for the second machine's and
  TLS's setup docs and goldens: 8.5 to 9, after core's model lands. 23.5 to 26 in all.

## 6. Acceptance contract

AT-001 to AT-004 run on one machine, with one local NATS server from `mashctl init --local`, scratch homes, no tool above mash installed,
no state from any earlier mash version. Each run produces the record of section 8.

### AT-001: the solo developer, standalone

Given a fresh scratch home, when the README quick start is followed (JRN-001: `init --local --owner alice`; for `design`
and `review`, `mash key create`, `endpoint create alice/dev/<name> --public-key`, `mash credential create`; plugin; two
sessions with `MASH_GROUP=dev`), then mail goes each way verified, `endpoint list --json` shows both with `group` `dev`,
the service metadata shows `agent` `claude-code` and the three parts, `mash admin permissions alice.dev.design` prints
REQ-005's set, and after `endpoint delete alice/dev/review` the review session's connection is closed, a reconnect is
refused, and `mash status` says why.

### AT-002: the key crosses no machine

Given two scratch homes A (mashctl host) and B (endpoint), when B runs `mash key create`, A runs `endpoint create
alice/dev/design --public-key` with B's public key file, and B runs `mash credential create` and connects, then the
endpoint mails a peer, a search of all captured output and of A's home for the seed finds nothing, and no captured
output contains the JWT.

### AT-003: every refusal can fail

Each case asserts the exit code, the refusal code in `--json`, a message naming what to type, and that nothing was
written (directory, issue record, streams, leases and files byte-identical before and after):

- `endpoint create design` with no group: `group_missing`, 2.
- `endpoint create alice/design`: two-token form, 2.
- `endpoint create alice/dev/design` with neither `--public-key` nor the same-host flag: `key_missing`, 2.
- A token that breaks REQ-001 (`Design`, `a--b`, 33 characters): `name_invalid`, 1. A token the name rule file refuses:
  `name_rule`, 1.
- An address that exists: `address_taken`, 1. A deleted, burned address: `key_retired`, 1.
- A malformed public key file: `public_key_invalid`, 1. A public key already issued at another address:
  `public_key_issued`, 1. A JWT output file that exists: `file_exists`, 1. No account key: `no_account_key`, 1.
- `mash credential create` with a seed and a JWT for different keys: 1.
- A session started with no `MASH_GROUP`: the process exits 2 with a message on standard error naming `MASH_GROUP`;
  afterwards no directory record, inbox stream, consumer or lease exists for that endpoint and no service is
  registered.
- `mashctl add`, `mashctl reissue`, `mashctl retire`: 2, each naming its replacement.
- Planted cross-owner attempt: with endpoints `alice/dev/design` and `bob/dev/build` on one server, `bob`'s session
  publishes to `agents.mail.alice.dev.design` and requests `agents.prompt.alice.dev.design`; the server refuses both
  with a permissions violation, and nothing arrives in alice's inbox. While alice's session has a service-discovery
  request in flight, `bob` publishes a forged discovery answer to alice's reply subject, and replays a genuine signed
  presence answer to it; the server refuses both with a permissions violation, and alice's discovery of an offline
  endpoint fails.

### AT-004: the command contract

Golden text and JSON for `endpoint create` (planned, created, each refusal), `reissue`, `delete`, `list`, `show`,
`mash key create`, `mash credential create` and the removed-command messages. `--dry-run` leaves the directory, the
issue record and the config directory byte-identical. The command-tree test of rule 22 walks the `endpoint`, `key` and
`credential` nouns (at most one positional, `--json` valid, `--dry-run` changes nothing, a bad flag exits 2, `--help`
has an example, no aliases) with only the named exceptions of REQ-013. Wherever mash's own code reads the time to
decide something in this contract (the locks of a concurrent create, issue times, revocation times), an in-process test
with an injected clock runs the skewed case inside and past the bound `docs/operations.md` states, and asserts that
two concurrent creates of one address never both succeed; the clock is injected in Go tests only, never through an
environment variable, flag or build tag of a shipped binary. If mash reads no clock for a decision, the record says so
and that case is not tested. A unit test signs for owner `alice` and asserts
that no permission line names another owner. A `create` run killed between the user being signed and the record being
written, run again, completes with one identity (NFR-001).

### AT-005: across machines, over TLS, on a cluster, from two mashctl machines

M1, M2 and M3 are rootless containers the test creates from an image it builds from mash's own repository: each has
its own filesystem, home, configuration, address and processes, on a network the test creates. A node reaches another
only over that network, by the address its certificate names, never over a shared file or loopback. No daemon outlives
the run, no operations template is used and nothing is placed on the host for the test. The test labels everything it
creates and destroys it at the end; a run killed half way leaves nothing that the harness's cleanup step, run again,
cannot remove by that label. If no rootless container runtime is present, the test fails with a message saying so; it
is not skipped, and the runtime is requested for the runner class as a tool, like a compiler.

Given the three nodes, each running one NATS server of one cluster, with TLS on client and route
connections under a certificate authority the test makes, one account, scratch homes and no tool above mash installed;
mashctl set up on M1 and on M2 as DEC-004 records, with `--servers 3`:

- From M1, `mashctl endpoint create alice/dev/design --public-key design.pub`, where `design.pub` was made by
  `mash key create` on M3; the JWT file is carried to M3, `mash credential create` runs there, and the session on M3
  connects to the server on M2. The new endpoint's credential is accepted by each of the three servers. Create changes
  no account record, so it reports no server acknowledgement.
- From M2, the same for `alice/dev/review`, whose key is made on M1 and whose session on M1 connects to the server on
  M3.
- Mail goes each way, verified. `endpoint list --json` run on M1 and on M2 shows both endpoints with `group` `dev`.
- From M2, `endpoint reissue alice/dev/design --public-key` with a new key made on M3: the old session is dropped, and
  the old key is refused on each of the three servers, and the command reports that all three servers acknowledged the
  account update. From M1, `endpoint delete alice/dev/review`: it reports the same acknowledgement, the session is
  dropped, a reconnect to each of the three servers is refused, and `mash status` says why.
- An endpoint pointed at a server URL without TLS on another machine refuses to connect (ADR 0108), and mashctl
  refuses an admin connection without TLS (ADR 0059).
- `endpoint create` of the same address from M1 and M2 at the same moment: one succeeds and the other is refused with
  `address_taken`; one identity exists afterwards.
- A revocation made from one mashctl machine is shown by `endpoint show` and `mashctl issued check` on the other.
- With an endpoint of a second owner on the cluster, it publishes a forged service-discovery answer and a replayed
  presence answer to the reply subject of a request from `alice`'s session in flight; the servers refuse both, and
  `alice`'s discovery of an offline endpoint fails.
- A search of every captured output, and of the homes on M1 and M2, finds no endpoint seed; no captured output on any
  machine contains a JWT.
